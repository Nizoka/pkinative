## [1.0.0] – 2026-10-04

### Security

- **fix(keys): the PBKDF2 work of a whole PKCS#12 is bounded** by the new limit `maxPkcs12KdfIterations` (CWE-400; the class of CVE-2022-36083): a 544-byte file made `openPkcs12` run 34 s, because only each derivation was bounded ([ADR 0020](docs/adr/0020-a-kdf-budget-per-pkcs12.md)).
- **fix(revocation): `PKI_REASON_REVOKED` only from authenticated, applicable evidence**; an unauthenticated claim is carried in `PKI_REASON_REVOCATION_UNKNOWN`.
- **fix(path): three name-constraint bypasses closed** — a URI host read by the RFC 3986 grammar, SmtpUTF8Mailbox (RFC 9598) held to rfc822Name subtrees, and the commonName fallback held to dNSName constraints through the new `CheckServerNameOptions.path`.
- **fix(crypto): id-RSASSA-PSS keys held to RFC 4055 §1.2 and §3.3.**
- **fix(path): a trust anchor is a name and a key** (RFC 5280 §6.1.1 (d); CWE-295): a self-signed certificate copying an anchor's name no longer ends the walk unverified.
- **fix(verify): a CRL issuer off the path is believed only once its own certificate validates under the same anchors** (§6.3.3 (f)): a forged delta or complete list from the sender's bag no longer clears a revoked certificate.
- **fix(path): `user-initial-policy-set` intersected in the anchor's domain** (§6.1.5 (g)(iii)), across policy mappings.
- **fix(crypto): an RSA public exponent below 3 or even is refused** (RFC 8017 §3.1); `PKI_DIAG_SPKI_RSA_EXPONENT_WEAK` at parse.
- **fix(verify): a SHA-1 timestamp imprint is not evidence without `allowSha1`.**
- **fix(keys): a PBMAC1 key shorter than 20 octets is not verified.**
- **fix(build): an ECDSA signing key without `namedCurve` is refused with `PKI_INVALID_OPTION`** instead of producing a certificate, request or SignedData whose signature verifies `false` (final review, 2026-10-04); `encodePem` quotes at most 64 characters of a bad label.
- **fix(revocation): `parseCertificateList`, `findRevocation` and `parseOcspResponse` enforce `maxInputBytes` and bound every walk by the field's arity** (CWE-400; second review, 2026-10-04): a 65 MiB root of two-octet values cost 40 s and 3 GB per reader, reachable through a chain report's `crls`/`ocspResponses`; refused in milliseconds now, with a time budget.
- **fix(verify, build, revocation, hash): the second review's minors** (2026-10-04): the chain report compares `crls`/`ocspResponses` byte for byte instead of keying them by their hex (CWE-400); `subjectPublicKey` must be one SEQUENCE, an extension value one DER value, an Edwards `ExternalSigner` signature 64 or 114 octets and an OCSP nonce 1 to 32 octets (`PKI_API_MISUSE`); `shake256` caps `outputLength` at 1 MiB and `checkOcspStatus` refuses a `NaN` or negative tolerance (`PKI_INVALID_OPTION`).
- **fix(path, revocation):** v1/v2 intermediates refused (§6.1.4 (k)); an IP-literal `dns` reference compared with iPAddress entries only; an unknown critical CRL entry extension makes the list unusable (§5.3); an OCSP answer without `nextUpdate` is stale by default and contradictory answers are UNKNOWN; a delegated OCSP responder is checked for revocation unless `id-pkix-ocsp-nocheck`; the reasons mask includes the certificate's distribution-point reasons; the implicit anchor counts against `maxChainLength`.
- **fix(asn1, crypto): two parser differentials closed** (CWE-436): the CRL/OCSP cursor refuses what the decoder refuses, an indefinite child is bounded by its parent, and RSASSA-PSS parameters are held to their grammar.
- **A CVE-class regression corpus**: 43 published vulnerabilities of comparable PKI libraries, each identifier checked against NVD or the GitHub Advisory Database, replayed by `tests/security/cve-classes.test.ts` and listed in `docs/data/cve-classes.json` with who stops each (`cve-class-parity`).

## [0.8.0] – 2026-09-29

### Added

- **feat(keys): private keys and PKCS#12, under PBES2 only** — the 0.8 band's subject, and the last subsystem that introduces error codes.

  **An encrypted key never exists in plaintext here.** An encrypted PKCS#8 — an `ENCRYPTED PRIVATE KEY`, or a PKCS#12 shrouded key bag — is opened with `unwrapKey`, which turns ciphertext straight into a non-extractable `CryptoKey`; the password becomes a PBKDF2 base key and is never used again, and `deriveBits` stays refused because `deriveKey` returns a handle where it would return bytes. `parsePrivateKeyInfo` describes a key — algorithm, curve, attributes, the v2 public key — without a field holding its secret. The one exception is stated rather than discovered: a writer may nest an *unencrypted* keyBag inside an encrypted SafeContents, and that key is plaintext once the SafeContents is opened; `readPkcs12` wipes those bytes as soon as Web Crypto has imported them, a best effort. The cost of the design is stated too: Web Crypto must be told what a key is *before* it decrypts it, so `decryptPrivateKey` takes the algorithm, and `readPkcs12` takes it from the certificate sharing the key's `localKeyId`.

  **PBES2 with PBKDF2 and AES-CBC is the one scheme opened, by policy.** RFC 7292's own schemes derive their key with the Appendix B KDF — iterated hashing with byte arithmetic over the password — and protect it with 3DES or 40-bit RC2. Every such scheme is still *described* by name, so `parseEncryptedPrivateKeyInfo` and `parsePkcs12` say what a file is protected with before anyone types a password, and refused with `PKI_KEY_ENCRYPTION_UNSUPPORTED`, whose remedy is a conversion run against OpenSSL 4.0.0 before it was written down. The password is UTF-8, as RFC 9579 and OpenSSL use it, or octets as given — not the BMPString of the KDF refused here. `maxKdfIterations` is checked before the host runs a single iteration, because the count is the file's to declare and runs where no JavaScript bound can reach.

  **Most PKCS#12 MACs cannot be verified, and the one call fails closed on them.** Even an OpenSSL 3 file encrypted with AES and PBKDF2 keys its MAC with Appendix B. `verifyPkcs12Mac` checks RFC 9579 PBMAC1 (OpenSSL 3.4 and later, `-pbmac1_pbkdf2`); `readPkcs12` reports anything else as `PKI_REASON_PKCS12_INTEGRITY_UNVERIFIED` unless the caller passes `allowUnverifiedIntegrity`, because without a MAC an unencrypted bag can be replaced by anyone who can write the file.

  **The Web Crypto door** opened `deriveKey`, `unwrapKey` and `decrypt` in its own reviewed commit, to the two boundary files only. A new `keys` layer never imports `x509`: describing a key file or a `.p12` ships neither the certificate parser nor the Web Crypto bridge (39.8 KB), and can run on a host with no `crypto.subtle`. `PkiKeyError` carries four codes, six `PKI_REASON_PKCS12_*` reasons say why a container was not opened, one diagnostic flags an iteration count below RFC 8018's recommended 1 000, and `maxKdfIterations` and `maxPkcs12Bags` join the named limits.

- **test(interop): the read direction, for key containers** — the interop matrix checked what pkinative writes; PKCS#12 and PKCS#8 are only read, so the arrow turns back. OpenSSL 4.0.0 (45 checks over 13 files) and Windows' .NET (18 over 4) write key containers that pkinative must open or refuse by name, and every key it opens signs data the foreign tool — not pkinative — verifies. It also records what those tools write by default: OpenSSL's `-export` keys its MAC with Appendix B, Windows exports 3DES, and .NET 9's AES export still uses the Appendix B MAC — so the only file pkinative can vouch for is one written with `-pbmac1_pbkdf2`, and the conversion documented in SECURITY.md is checked to produce one.
- **feat(docs): the error-code vocabulary frozen at 0.8.0** — `docs/data/errors.frozen.json` holds the 57 codes, and the `error-codes-frozen` rule fails on a removal, a rename or a class move, which from this release are semver-major. `error-parity` found a hole in itself on the way: it checked a throw site's message but never its code, so a computed code could make the codes reachable at run time differ from the registry. It now decides every code from the syntax tree, following one passed through a typed helper to every caller; `src/` had no violation. `pkcs12-policy-parity` holds SECURITY.md's table of what is opened and refused to the code, both ways.

### Fixed

- **fix(verify): a CRL entry the walk cannot read is reported, not thrown** — `parseCertificateList` reads a list's envelope and counts its entries; the entries are read later, and that later read was outside any catch. A list with sound framing and an entry missing its revocation date made `verifyCertificateChain`, `verifySignedData` and `verifyTimeStampToken` throw. Found by a seeded fuzzer that now drives all the one-call reports with structural mutations and tiny limits.
- **fix(verify): misuse throws before the reports' catch** — the opposite leak, found by the same work: an unknown limit, a bad option, an argument that is not bytes or a certificate `parseCertificate` did not make was converted into a reason, or escaped as a `TypeError`. Each report now decides misuse before anything is read.
- **fix: a caller's type error is `PKI_INVALID_INPUT`** — `parseTimeStampResponse`, the TimeStampReq reader and `parseCertificateList` threw a `TypeError` or a length error for an argument that is not bytes; and a reason about a CRL now names where the caller put it rather than its position among the lists that parsed.
- **fix(keys): a key shrouded under a refused scheme is reported under that scheme** — in exactly the files `openssl pkcs12 -legacy` and Windows' `X509Certificate2.Export` write, the 3DES-shrouded key was reported as `PKI_REASON_PKCS12_KEY_UNMATCHED`: its certificate looked absent only because the same refusal kept the certificate bag shut, so the remedy that reason gives could never work. It is now `PKI_REASON_PKCS12_ENCRYPTION_UNSUPPORTED`, naming the scheme. Found by the interop run below.
- **fix(verify-docs): `count-tokens` read "Twenty-one" as "one"** — compound number words are parsed, so a count past twenty written in words is held to its source too.

## [0.7.0] – 2026-09-29

### Added

- **feat(cms): CMS SignedData and RFC 3161 timestamps, parsed, built and verified** — the 0.7 band's subject, in the same split every other subsystem keeps: parsing in `cms/`, the signature at the Web Crypto door in `crypto/`, writing in `build/`, and the verdicts in `verify/`.

  **Reading.** `parseSignedData` reads RFC 5652 SignedData — signers, certificate and revocation bags (RFC 5940 OCSP responses included), and the signed attributes both decoded and exposed as `signedAttributesDer`, **re-tagged as the SET they were signed under** rather than the `[0]` they travel under, because that is the byte string a signature covers and the one a verifier most often gets wrong. A recognised attribute is decoded only when it appears exactly once with one value. `parseTimeStampResponse`, `parseTimeStampToken` and `parseTstInfo` read RFC 3161; a structural failure throws `PkiCmsError` with one of four new `PKI_CMS_*` codes, and four `PKI_DIAG_CMS_*` diagnostics report what is merely non-canonical.

  **Writing.** `createSignedData` signs attached or detached content and writes the attributes a verifier checks — `contentType`, `messageDigest`, `signingTime`, ESS `signingCertificateV2` and RFC 6211 `CMSAlgorithmProtection` — with a `Signer` that is either a Web Crypto key or an **`ExternalSigner`**, for a key that lives in an HSM or behind a remote service and never enters the process. `createTimeStampRequest` builds the request, and `addUnsignedAttribute` / `addTimeStampToken` splice into a signer without disturbing one signed byte.

  **Judging.** `verifySignedData` checks every signer — attributes, algorithm agreement (RFC 8933, 4056, 5753, 8419), digest, signature, ESS binding — then its chain, and reports `intact` apart from `valid`: *the message is what its signer signed* against *and somebody you trust signed it*. `verifyTimeStampToken` checks a token against the request, the data or the imprint, and holds the TSA to RFC 3161 §2.3's critical, exclusive `timeStamping` purpose. With `atTimeStamp`, a signer is judged at the earliest instant a verified timestamp proves — which is how a signature outlives its certificate — while the TSA's own chain is always judged at `at`, **never at the `genTime` it wrote itself**. Eleven `PKI_REASON_CMS_*` / `PKI_REASON_TSP_*` reasons say why a verdict is no.

  **Architecture.** Two layer edges change in their own reviewed commit: `cms → types, core, asn1, hash, x509, build`, and `verify` gains `cms`. `cms` never imports `crypto`, for the reason `path` does not: verdicts arrive precomputed, so parsing and judging stay synchronous.

- **feat(conformance): L8, the 224 NIST PKITS S/MIME messages verified whole** — each message linked to its test through its own `SignerIdentifier` rather than a table of names, and verified by `verifySignedData` with L7's anchor, lists and instant and only the certificates it carries. Two claims, scored apart: **221 of 224 are intact at the CMS layer** (the three that are not are DSA, which Web Crypto does not implement), and **every one of 204 scored verdicts equals the L7 verdict on its signer's own path**. 195 of 204 agree with NIST (95.59 %) — L7's nine deviations, and no others.

### Fixed

- **fix(verify): a revocation list passed twice was read twice** — a signed message carries the CRL its signer relied on, the caller passes the one they downloaded, and `verifyCertificateChain` reported every revocation once per copy. Lists and stapled OCSP responses are now read once per distinct encoding. Found by L8, whose 20 pins on the doubled codes were re-reviewed.
- **fix(verify): `requireRevocation` reaches the timestamps** — `verifySignedData` passed the caller's CRLs and OCSP responses to each timestamp but not the requirement, so a TSA nobody could check for revocation still counted as evidence for `atTimeStamp`.
- **fix(revocation): an OCSP response carrying a recognised extension was refused** — the defect the CRL parser shipped in 0.5, in the OCSP reader, hidden because the nonce a response usually carries is an extension the certificate reader never decodes. Found while writing the TSTInfo reader.

## [0.5.0] – 2026-09-28

### Added

- **feat(revocation): delta CRLs, and who is allowed to sign one — 194 of 203 NIST paths** — two lines of the 0.5 roadmap, and between them the last of RFC 5280 §5's revocation machinery.

  **§5.2.4 delta CRLs.** A delta lists what changed since a complete list, so reading it alone reports every certificate absent from it — nearly all of them — as unrevoked, and ignoring it keeps refusing a certificate long after the CA withdrew the revocation. `CertificateList` now carries `baseCrlNumber`, and `checkRevocation` takes the delta beside the base it applies over: **the delta is asked first, and the base only where the delta is silent.** That order is the rule, which is why the pair goes into one call rather than being merged by the caller — and it is the only place `removeFromCRL` can mean what it means, since it appears on a delta to withdraw what the base still records. The pairing bounds the two on both sides (the base's `cRLNumber` at least the delta's `BaseCRLNumber` and below the delta's own), refuses a delta nobody vouched for, and refuses one whose scope does not cover the certificate. A delta handed over as `crl` is still refused outright.

  **Who may sign a list, in three parts.** The `authorityKeyIdentifier` on a list is the CA saying which of its keys revokes — without it, any certificate carrying the CA's name and `cRLSign` will do, which is what makes a key rollover work and what cannot tell a designated signer from an undesignated sibling. And a key the CA *delegated* the job to must hold a certificate that is still in date and **not itself revoked**: without that last rule, withdrawing a compromised CRL-signing key means nothing at all, because whoever holds it goes on publishing *"nothing is revoked"* until the certificate expires. That check is bounded by rank rather than by a depth counter — a delegated signer is judged only by a list the path itself vouches for, a certificate on the path is judged by §6, and there is no second level to terminate.

  **NIST PKITS 191 → 194 of 203 (95.57 %)**, x509-limbo unchanged at 9 156/9 208. Nine deviations remain, and one of them accepts what a standards body rejects: `InvalidDNandRFC822nameConstraintsTest29` accepts — its end-entity certificate has no subjectAltName and an `emailAddress` in its subject outside the permitted `rfc822Name` subtree, and RFC 5280 §4.2.1.10 applies the constraint to that address, which pkinative did not; five are RFC 5280 §7.1 name comparison (encoded bytes, as Go and webpki), each a refusal; two are DSA, and one is a suspected defect in §6.1.5's policy wrap-up, recorded alone for that reason. The corpus also corrected a diagnosis made here first: the roadmap said `InvalidSeparateCertificateandCRLKeysTest21` was about matching key identifiers, and measurement showed the designated signer was simply revoked — the key-identifier rule is right and was not what that test was testing.

- **feat(revocation): what a CRL is *about* — RFC 5280 §5.2.5, §6.3.3 (b) and §5.3.3, and 191 of 203 NIST paths** — a revocation list is evidence of **absence**: your serial is not on it. Evidence of absence is worth exactly what the list's declared scope says it is worth, and until now pkinative read every list as covering everything its CA had ever issued. A CA that publishes one list for its end-entity certificates and another for its sub-CAs marks both with `issuingDistributionPoint`; a verifier that ignores the mark reads a sub-CA's absence from the end-entity list as a clean bill of health, **and accepts every certificate under a CA its own issuer has revoked**. RFC 5280 requires that extension to be critical for exactly this reason.

  So `CertificateList` now carries `issuingDistributionPoint`, and deciding whether a list may answer about a certificate is a step of its own: the §5.2.5 kind rules (`onlyContainsUserCerts`, `onlyContainsCACerts`, `onlyContainsAttributeCerts`), the §6.3.3 (b) agreement between the certificate's `cRLDistributionPoints` and the list's own point — **including names given relative to the CRL issuer**, composed RDN by RDN on encoded values rather than by re-rendering a name that would stop matching a TeletexString — and the indirect case, where the CA delegates to a `cRLIssuer` and the list must itself assert `indirectCRL`. Without that last agreement, any CA named in any `cRLIssuer` field could answer for certificates it never issued. `findRevocation` gained `issuerDer` and the §5.3.3 `certificateIssuer` running state that goes with it: on an indirect list a serial is not an identity, because two CAs issue the same serial all the time.

  **A list is refused in three new ways, and each one is a different sentence.** `PKI_REASON_REVOCATION_OUT_OF_SCOPE` is the right CA's wrong list — a different remedy from `WRONG_ISSUER`, which sends you to a different CA entirely. `PKI_REASON_REVOCATION_PARTIAL` says what a list with `onlySomeReasons` actually ruled out; it is a code rather than a wording of `UNKNOWN` because **partial answers add up**, and `verifyCertificateChain` adds them: a CA publishing a keyCompromise list it can reissue in minutes and a second list for the rest has answered completely, which is §6.3.3's `reasons_mask` and which no single list can see. And `PKI_REASON_UNRECOGNISED_CRITICAL_EXTENSION` now reaches CRLs too — §6.3.3 says a list carrying one MUST NOT be used, in the same words §6.1.3 (f) uses for a certificate. A delta CRL is refused outright until §5.2.4 lands, because a delta read as complete reports every certificate absent from it as unrevoked.

  Measured against NIST PKITS the score went from 177/203 to **191/203 (94.09 %)**, with x509-limbo unchanged at 9 156/9 208 — and the corpus overturned a decision made here first: `nameRelativeToCRLIssuer` was going to be refused rather than composed, on the grounds that nothing real uses it. NIST builds four tests on it, and refusing turned four valid paths into unproven ones. Twelve deviations remain, and one of them is recorded alone because it is the only entry in that baseline that **accepts** something a standards body says to reject: a revocation published only on a delta CRL is missed until §5.2.4 is implemented.

- **feat(hash): `computeKeyIdentifier`, and the two diagnostics it unblocked** — RFC 5280 §4.2.1.2 method 1, *"the SHA-1 hash of the value of the BIT STRING subjectPublicKey, excluding the tag, length, and number of unused bits"*, which is also byte for byte RFC 6960 §4.1.1's `issuerKeyHash`. Computing it once and naming it once is why it lives in `hash/` rather than being written twice; `encodeCertId` now calls it, so the two cannot drift into hashing different things. **The input is the key bits, not the SubjectPublicKeyInfo** — hashing the SPKI produces an OCSP request every responder answers `unknown` to and an identifier that matches nothing, and it is the single most common mistake in this corner.

  With the builder able to write them, `PKI_DIAG_AKI_MISSING` and `PKI_DIAG_SKI_MISSING` land — each under the condition the RFC actually sets, and each measured before it was added: absent from 0.7 % and 1.3 % of x509-limbo, which is signal rather than chatter. §4.2.1.1 exempts a certificate that names nobody above it, so a self-signed root is never reported; §4.2.1.2 requires the subject identifier of **CA** certificates, and reporting a SHOULD on every end-entity certificate in existence would be chatter. Neither fires on a v1 or v2 certificate, which has nowhere to put an extension — that would be reporting the format rather than a choice the issuer made. Neither is a verdict: the field is a hint a path builder uses to order candidates, and `buildCertificatePath` works by name.

- **feat(verify): `verifyCertificateChain` — the one call, and the only place that catches** — every layer below answers exactly one question and is deliberately blind to the others: §6 has no notion of the host you connected to, `checkServerName` knows nothing about trust, `checkExtendedKeyUsage` knows nothing about time, revocation takes a signature verdict it did not compute. That separation is what keeps each of them synchronous, pure, fuzzable and small — and it leaves somebody with the job of putting them in the right order. **If that somebody is every caller, every caller gets it slightly wrong.**

  So it is here, once, in a new `verify` layer: every signature the search could need verified **in parallel before anything is decided**, the path built with the purpose already in hand, then the host name, then revocation. `at` defaults to now. Revocation is soft-fail unless `requireRevocation` says otherwise, because a library that refuses every chain for which the caller happened not to download a list is a library callers route around. SHA-1 signatures come back `PKI_REASON_SIGNATURE_NOT_CHECKED` rather than believed. `VerifyChainReport` adds `verified`, the number of signatures computed — worth logging, because a number far above the path length is what a bag full of plausible issuers looks like.

  **Revocation takes `crls`, `ocsp`, or both.** A CRL is used when it names the CA that issued the certificate **and** that CA asserts `cRLSign` — a CA constrained to signing certificates may not revoke them (RFC 5280 §4.2.1.3), and `signatureVerified` already documented itself as asking whether *a key entitled to sign it* did. An OCSP response is matched on **all three** `CertID` fields, under the digest the responder actually used, and its signer is authorised the way RFC 6960 §4.2.2.2 sets out: either the issuing CA signed it, or the CA issued a certificate carrying `id-kp-OCSPSigning` and **that** certificate signed it. The certificates a response *attaches* are a convenience for reaching that delegate, never a claim of authority — each is checked to have been issued by this CA, to carry the purpose and to be in date before its signature counts for anything, because a client that trusted the attached bag would let the responder nominate itself, which is the whole reason §4.2.2.2 exists.

  **This is the module that finally produces `PKI_REASON_INPUT_MALFORMED`**, and it is the only one in `src/` that turns a `PkiError` into a reason. The rule the library runs on — *primitives return and throw, compositions report, exactly one layer converts* — was written in 0.5's first commit with nothing yet obeying the last clause; a malformed CRL is now a reason carrying in `errorCode` the code that would have been thrown. What it does **not** do is fetch: not a CRL, not an OCSP response, not a missing intermediate. A verifier that reached the network would be one an attacker can point at a host of their choosing.

- **feat(conformance): NIST PKITS, the second corpus — 177 of 203 NIST paths agree** — L6 proves agreement with **one** corpus. Two written independently is a different claim, and it is the only one that catches a misreading the first shares: x509-limbo comes from the Python cryptography project and is built around the Web PKI, PKITS from NIST around the US Federal PKI, with certificate policies, policy mapping, key rollover and indirect CRLs the Web has never used. Every one of the 405 certificates and 173 lists parses, with **no reviewed refusal list at all** — a certificate a standards body publishes in a conformance suite and this library cannot read is a defect here, not a decision.

  **The expectations come from the file names and nowhere else.** PKITS states its results in a PDF, and parsing one to decide what a gate expects makes the gate as stable as a text-extraction heuristic. NIST's own convention is machine-readable: `Valid…Test1EE.crt` must succeed, `Invalid…` must fail, and 203 of the 223 tests say so in their own name. The other 20 are §4.8 policy tests whose answer depends on a `user-initial-policy-set` the archive never states — skipped with that reason rather than guessed. **The path is built, not transcribed**: the whole bag of 404 certificates goes to `buildCertificatePath` every time, so each test also exercises path building on a candidate set with cross-certificates and rollovers in it.

  The archive is pinned **twice**, because one digest cannot do both jobs: its own SHA-256 fixes every byte NIST published — which matters more than for a repository, since NIST publishes no version and overwrites the same URL — and a per-file list fixes what this project's own ZIP reader made of it. That reader (`scripts/lib/zip.ts`, about a hundred lines over `node:zlib`) reads the central directory as the truth and checks the local header agrees on the name, bounds-checks every offset, refuses `..` and absolute paths, and refuses Zip64 rather than half-reading it. And the instant every test is judged at is **fixed, not `Date.now()`**: the corpus lives between 2010 and 2030, and a gate asking about today would answer the same thing until 2031 and then go red for reasons having nothing to do with this library — the runner fails with that message instead.

- **feat(conformance): x509-limbo *scored*, and every disagreement carrying a sentence** — L1–L5 prove that pkinative parses what other implementations parse. L6 scores the other half: for each of the corpus's 9 793 cases it builds a path, matches the host name and consults the CRL the way a caller would, and its verdict must match the one the corpus writes down. Nothing before 0.5 could produce that number, because nothing validated a path.

  **Three things make it evidence rather than a statistic.** Reason codes, not the boolean: a reviewed subset is pinned on its `PkiReasonCode`, because *rejected for the wrong reason* is a defect no pass/fail count can see. Canaries: one case that must succeed and one that must fail, so a harness whose trust store silently stopped being passed through cannot score well against a corpus that is mostly FAILURE. And **every deviation carries a written reason** — `--update-baseline` records the id it measured and never fills in the `why`, so an unexplained disagreement fails the gate. A baseline a tool can complete unattended is one that quietly absorbs regressions.

  **It scores the call callers make.** The runner composes nothing: it unwraps PEM, translates the corpus vocabulary into the library's — `validation_kind` into a key purpose, `max_chain_depth` into a chain-length bound — and hands the whole question to `verifyCertificateChain`. A harness that arranged the primitives itself would score an arrangement that ships in no package, and the arrangement is exactly the part a caller is most likely to get wrong. It cost the signature cache an earlier version kept, about a fifth more work, and it immediately found a shipped defect in the CRL parser that the hand-rolled harness had been hiding.

  A lazier scheme was tried and measured being wrong, and the comment saying so is in the module: verifying only the links of the path the builder reports stalls, because with no verdicts every path fails identically, the report is the *deepest* attempt — often a decoy — and once the decoy is known invalid it is still the deepest. Fifteen cases the corpus expects to succeed were refused that way. So every pair the builder could use is verified up front, restricted to the certificates a name chain from the leaf can reach.

- **feat(path): `checkExtendedKeyUsage` — may this chain be used for *this*?** — a validated path says a CA vouched for a certificate and `checkServerName` says the certificate names the host you asked for. Neither says the certificate is **for** what you are about to do with it, and a certificate issued for signing e-mail, accepted to authenticate a TLS server, is one used outside the purpose its subject asked for and its issuer granted. §6 never reads `extKeyUsage` — RFC 5280 §4.2.1.12 leaves the consequence to the application — so which purpose you need is an argument rather than a guess, exactly as the host name is.

  **`buildCertificatePath` gained `requiredPurposes`, and scoring the corpus is what showed why it had to.** A builder that picks a path without knowing what the path is for will confidently return one the purpose check then condemns **while an acceptable path existed** — two x509-limbo cases are exactly that shape, a bag of six cross-signed intermediates of which some are restricted to `emailProtection`, and both expect success. Whatever can make a path unacceptable belongs inside the search, for the same reason name constraints are inside §6 rather than after it. `validateCertificatePath` is untouched: §6 has no notion of purpose, and searching is not §6.

  **A CA's own `extKeyUsage` restricts what it may issue for, and that rule is on by default.** No sentence of RFC 5280 states it; every Web PKI validator enforces it, and the CA/Browser Forum relies on it to constrain technically-constrained sub-CAs — without it, a sub-CA restricted to `emailProtection` issues a `serverAuth` certificate and the chain validates, which is the whole point of restricting it. `restrictIssuers: false` is the literal-RFC reading, offered because an internal PKI may put a purpose on a CA as documentation. An **absent** extension means unrestricted (§4.2.1.12), which is why almost no public root appears in a refusal; `requireExplicit` is the stricter reading and applies to the end entity alone, because requiring every CA to enumerate the purposes of everything it may ever issue is not a reading anyone holds. `anyExtendedKeyUsage` permits every purpose, as the RFC defines it. New reason `PKI_REASON_PURPOSE_NOT_PERMITTED`, which distinguishes *absent* from *naming something else* — the two call for different conversations with the CA.

- **feat(x509): six profile diagnostics, each one a sentence addressed to the CA** — `PKI_DIAG_NAME_CONSTRAINTS_IN_END_ENTITY`, `PKI_DIAG_BASIC_CONSTRAINTS_NOT_CRITICAL`, `PKI_DIAG_POLICY_CONSTRAINTS_NOT_CRITICAL`, `PKI_DIAG_KEY_CERT_SIGN_WITHOUT_CA`, `PKI_DIAG_COMMON_NAME_NOT_IN_SAN` and `PKI_DIAG_DNS_NAME_NOT_PREFERRED_SYNTAX`. Each answers an x509-limbo case that expects a *refusal*, and each stays a diagnostic for the same reason: the "MUST" is addressed to the issuing CA, pkinative reads and enforces the extension whatever the profile says about its criticality, and refusing the chain would make this library stricter than RFC 5280 asks of a verifier while accepting exactly the same set of chains. `strict: true` escalates them, which is where that choice belongs.

  **Which diagnostics to add was decided by measuring, not by taste.** A missing `authorityKeyIdentifier` or `subjectKeyIdentifier` is absent from 0.7 % and 1.3 % of the corpus — a real signal — and is nonetheless *not* reported, because reporting it means `createCertificate` has to be able to emit both extensions or everything this library builds trips its own reader. That is its own change, and the reason is recorded beside the cases it would answer. `PKI_DIAG_COMMON_NAME_NOT_IN_SAN` fires only for a `commonName` that could be matched **as a host**: `CN=Example Issuing CA` is not such a name, and reporting it would be reporting the ordinary shape of every organisational subject, which is how a diagnostic channel gets ignored. `PKI_DIAG_COMMON_NAME_NOT_IN_SAN` is also the first diagnostic to cite CA/Browser Forum Baseline Requirements rather than an RFC, because no RFC says it.

- **feat(path): `checkServerName` — does this certificate name the host you asked for?** — a validated chain says a CA vouched for a certificate. It says nothing about which host the certificate is *for*, and RFC 5280 §6 never will: it has no notion of the name you asked for. Without that second question a valid certificate for `attacker.example` is accepted as one for `bank.example`, so this lands beside `validateCertificatePath` as its own capability rather than as an option on it.

  RFC 6125 written the strict way, because every relaxation has been somebody's bypass: `subjectAltName` is authoritative whenever it carries a `dNSName` or an `iPAddress`, and the `commonName` fallback is **off by default** because CA/Browser Forum BR 7.1.4.2.2 has forbidden CN-only certificates since 2017. A wildcard is one whole leftmost label and needs three of them; partial wildcards are refused whatever §6.4.3 once allowed. An address is compared as **octets, never as text**, and the two forms never cross — `1.2.3.4` written as a `dNSName` is a whole class of bypass. No public suffix list is embedded: that is data which changes weekly, and a parser carrying a stale copy is worse than one that says it does not know, so registry-level policy stays with the caller.

- **feat(path): a signature verdict now names its issuer** — `SignatureResult` gains an optional `issuer`. Keyed by the subject alone, a verdict says *"this certificate's signature is good"* without saying good under **which** issuer — and one certificate can be properly signed by one CA and forged under another of the same name. That is cross-signing, the case `buildCertificatePath` exists for, so keying by subject made the very bags this function was written for undecidable: whichever verdict was passed last decided the chain. The pair is looked up first, and two issuer-less verdicts that **disagree** are `PKI_REASON_SIGNATURE_NOT_CHECKED` rather than resolved by order. Ambiguity is an answer; guessing is how the decoy half of a cross-signed pair gets accepted. Agreeing duplicates still pass, because they say the same thing whichever issuer was meant.

### Changed

- **A SHA-1 signature is refused rather than answered** — `PKI_CRYPTO_ALGORITHM_REFUSED` (new). Web Crypto computes SHA-1 quite happily, which is the problem: a chosen-prefix collision has been practical since 2017, so the signature does not bind the bytes it covers, and `verifyCertificateSignature` was returning `true` for it. Neither boolean is honest — the arithmetic may well check out, and it still shows nothing — so the answer is a `PkiCryptoError`, which is what that family means: *this question cannot be put*. The path validator turns it into `PKI_REASON_SIGNATURE_NOT_CHECKED`, so a chain signed over SHA-1 is refused with a reason a reader can act on. `allowSha1` exists for examining a historical artefact, never for authenticating with one, and `verifyOcspSignature` has no opt-in at all — a revocation answer has no archival reading to make room for. A certificate's SHA-1 **fingerprint** is untouched: that is a digest of public data, not a signature.

### Fixed

- **fix(verify): a revoked CA was accepted, and a CRL had only one chance to be believed** — both found by NIST PKITS, and both in the composition rather than in the primitives.

  `verifyCertificateChain` asked about the **leaf only**. A revoked intermediate is a revoked chain: the CA whose key signed the leaf has had that key withdrawn, and a verifier that asked no further accepts everything below a CA its own issuer had disowned — which is the shape a compromised sub-CA takes. Every certificate on the path is now checked, the trust anchor excepted, because a list a root issued about itself revokes nothing.

  And the list's signature was tried against **one** certificate, the one sitting above the leaf. A CA is a name, not a key: a rollover leaves two live at once, and PKITS has a CA that signs certificates with one key and its lists with another. The signer is now looked for among every certificate in the path and the candidate bag that carries the list's issuer name and asserts `cRLSign`, and the first that verifies settles it.

  **Checked everywhere, required at the leaf** — those are two questions and collapsing them gets one wrong. Requiring an answer about every certificate would be unusable: a stapled OCSP response answers about the end entity and nothing else, nobody fetches a CRL for an intermediate on the connection path, and the Web PKI handles intermediates out of band through CRLSets and OneCRL. So `requireRevocation` still demands an answer about the certificate a caller can actually obtain one for.

- **fix(revocation): every CRL carrying a recognised extension was refused** — and it took pointing the conformance scorer at `verifyCertificateChain` to notice, which is the whole argument for scoring the call callers make. `_decodeExtension` decodes an extension value **in place** and refuses octets sitting behind it inside `extnValue`, so it needs the offset of the value's content and a buffer that ends where the value ends. The certificate parser hands it exactly that; the CRL reader handed it the `Extension` SEQUENCE's own offset and the whole file, so the decoder read the SEQUENCE as the value and saw the rest of the CRL behind it. Every CRL with an `authorityKeyIdentifier` — which is every CRL in the wild — was `PKI_X509_EXTENSION_MALFORMED`.

  The suite had eleven CRL-extension tests and none of them caught it, because `cRLNumber` and the delta marker are read from their raw value and never reach the decoder table: every existing test used an extension pkinative does **not** decode. The locking test uses one it does. The four `crl::` cases of x509-limbo would have caught it too, and did not, because the old harness marked a CRL it could not parse as *unparsed* and moved on — a scorer quietly declining to answer is worse than one that answers wrongly, and that is now a reason rather than a shrug.

- **fix(path): ten ways a name escaped its constraint, and the anchor that was never judged** — all found by scoring the corpus rather than by review, and each one let a constrained CA issue a name its issuer had withheld.

  **A malformed name is not inside the permitted namespace.** `.example.com` is not a host name and `invalid@address@example.com` is not a mailbox, yet both suffix-match `example.com` and were called permitted. §6.1.3 (b) requires every name to be *located within* the permitted subtrees, and a name that cannot be located is not within them. A trailing dot goes the same way: the matching rules do not strip it, so calling it well formed left it silently matching nothing, which reads as "unconstrained".

  **A URI constraint without a leading period names one host, not a domain.** The RFC spells out the asymmetry — *"When the constraint does not begin with a period, it specifies a host"* — and routing URIs through the `dNSName` rule let a CA constrained to one host issue for every subdomain of it.

  **A constraint on a form this module does not process must refuse.** §4.2.1.10 leaves no third option: process every constrained form or reject. Skipping an `otherName` constraint answered "unconstrained" to a CA that said "forbidden".

  **A wildcard is a set, not a string.** `*.example.com` denotes every single-label host under `example.com`, so an exclusion of `bar.example.com` names one of its members and must refuse it, while a permission has to cover the whole set rather than one spelling. This is **CVE-2025-61727**. A star anywhere in a label counts, because a matcher lenient enough to honour `w*.example.com` would expand it onto an excluded name; over-approximating the set can only refuse, never permit.

  **The trust anchor is judged, not just trusted.** Its validity window and its critical extensions are now checked whichever input the caller put it in — a certificate judged differently depending on that is one nobody can reason about. Trusting a key is not believing its owner still holds it: an expired root is one whose owner retired it, and an unknown critical extension on it is an instruction this validator cannot follow.

  And two clauses of §6.1.3 and §6.1.4 that were missing: name constraints are **not applied to a self-issued certificate** unless it is the final one, and a self-issued certificate **spends no path-length budget** — a CA re-keying itself adds a certificate to the path without adding a link to the hierarchy, and charging it a step refused a rollover that fits the constraint its issuer wrote.

- **feat(path): path *building*, because a caller has a bag and not a chain** — `validateCertificatePath` takes an ordered chain; real callers do not have one. A TLS handshake hands over an unordered `certificate_list`, a trust store holds hundreds of anchors, and **cross-signing means one subject name can have several plausible issuers** — Let's Encrypt's own hierarchy is the everyday case, and a verifier taking the first match fails on chains that validate perfectly through the other. So `buildCertificatePath` is a depth-first search with backtracking, and the test for it constructs exactly that shape: two CAs with the same subject name, only one of which leads to the trusted root, with the decoy first.

  **The bound is `maxPathsExplored` (new, 1 000, CWE-400), not `maxChainLength`.** Building is exponential in the candidate set and only linear in the chain length, which makes it *the* denial-of-service vector of §6: a bag of thirty certificates that all name each other as issuer is a few kilobytes of input and unbounded work. The report carries `explored`, which is worth logging — a number near the bound is a bag designed to be expensive, not a hierarchy — and the budget abandons the whole search rather than the branch it ran out on, or it would be spent again at every level.

  Signature verdicts still arrive precomputed, which is the awkward part of building rather than validating: a caller does not know in advance which pairs will be tried, so they verify every plausible pair up front and pass them all. A pair with no verdict fails closed. When no path is accepted the report carries the reasons from the attempt that got **furthest**, because "no path found" without saying why is a report nobody can act on. Choosing which anchors to trust is the caller's, and so is fetching anything not already in the bag — a path builder that reached the network would be one an attacker can point at a host of their choosing.
- **feat(revocation): the OCSP status decision, and the substitution it catches** — `checkOcspStatus` reports all four of RFC 6960 §3.2's client responsibilities: the answer is about the certificate asked about, the signature verified, the signer is authorised, and the answer is fresh. The middle two arrive as **verdicts the caller computed**, which keeps the decision synchronous and keeps policy out of the library — RFC 6960 §4.2.2.2 gives three routes to authorising a responder and choosing one is not a library's call.

  **`PKI_REASON_REVOCATION_MISMATCH` is a separate code from `UNKNOWN`, because the two call for different actions.** `UNKNOWN` means ask again; a mismatch means *this answer is not yours* — a confused responder, a cache serving somebody else's response, or an attacker substituting one. Retrying a mismatch against the same responder is the wrong move, and a caller that could not tell them apart would do it. The answer is located by matching **all three** `CertID` fields, never by taking `responses[0]`: a response may carry several, and taking the first is how a client reads somebody else's status as its own. The report names which field diverged and both values, so it can be acted on.

  Three nuances that are the opposite of the CRL rules, and are deliberate. A nonce that comes back **different** is always a mismatch; one that does not come back **at all** is reported only when `requireNonce` asks, because the CA/Browser Forum discourages nonces so responses stay cacheable and most public responders omit the echo — which matters more is the caller's choice, not a default. The nonce sits inside **two** OCTET STRINGs, and a check at the wrong layer passes on everything, so an echo wrapped one layer short or carrying a long-form length is a mismatch rather than something to unwrap generously. And a **missing `nextUpdate` is not stale here**: RFC 6960 §4.2.2.1 says its absence means newer information is always available, the opposite of the CRL case where nothing promises a successor. `futureTolerance` (a minute) refuses a `thisUpdate` well ahead of now, because clocks disagree by seconds and not hours.
- **feat(revocation): RFC 6960 OCSP, both directions, with three states kept three** — `createOcspRequest` builds the bytes you POST, `parseOcspResponse` reads what comes back, `verifyOcspSignature` checks the responder signed it, and `encodeCertId` is exported so a caller matching an answer to a question recomputes the same three values rather than doing it by hand.

  **`good`, `revoked` and `unknown` are three states because RFC 6960 §2.2 makes them three.** `unknown` is the responder saying it does not know about this certificate — an absence of evidence, the OCSP form of the same distinction `PKI_REASON_REVOCATION_UNKNOWN` draws for CRLs. The six non-`successful` statuses are the responder declining to answer at all, and a response carrying one has **no** `basicResponse`, because the protocol carries no body there — both directions of that are refused, so neither a bodiless success nor a bodied refusal parses.

  **`issuerKeyHash` is over the public key bits, not the SubjectPublicKeyInfo.** That is the single most common OCSP client bug: hashing the SPKI produces a request a responder answers `unknown` to, which a careless client reports as not revoked. The recipe asserts all three hashes — that the key hash equals SHA-1 of `publicKey.bytes`, that it does **not** equal SHA-1 of the SPKI, and that the name hash is over the encoded `Name` — because getting the first right by accident while the second also matched would prove nothing. SHA-1 is the default because RFC 6960 §4.3 makes it mandatory for responders and a SHA-256 `CertID` comes back `unknown` from many of them. The nonce is the caller's own random bytes: pkinative generates none, and it goes inside **two** OCTET STRINGs, which is the layer a responder silently ignores when it is missing. New limit `maxOcspResponses` (256, CWE-400).

  What this does **not** do is decide which certificate may answer for a CA. `basicResponse.certificates` are certificates the responder *attached*; trusting them because they arrived would let the responder nominate its own authority, which is what RFC 6960 §4.2.2.2 exists to constrain. `verifyCertificateSignature`, `verifyCrlSignature` and `verifyOcspSignature` now share one `verifySignedStructure`, with the inner algorithm field optional — a certificate and a CRL name the algorithm twice and OCSP names it once, so the match check is skipped rather than faked.
- **feat(revocation): the revocation decision, and the four answers it keeps apart** — `verifyCrlSignature(crl, issuer)` checks that a CA's key signed a list, and `checkRevocation` decides a certificate's status against it. `checkRevocation` takes a **precomputed signature verdict** rather than a key, exactly as path validation does, which is what keeps it synchronous, pure and free of Web Crypto — `verify-bundle` weighs the claim. The two verification functions now share one `verifySignedStructure`, because a certificate and a CRL *are* the same signed structure and writing that shape down once means a CRL cannot end up with a laxer signature check than a certificate — which is how a revocation list gets accepted from someone who did not issue it.

  **`PKI_REASON_REVOCATION_UNKNOWN` is not `[]`, and that distinction is the feature.** A missing or unsigned list is an absence of evidence; reporting it as "not revoked" would make the soft-fail decision on the caller's behalf, invisibly. `staleTolerance` is the same idea for a lapsed list — a number the caller writes, not a default that chose for them. A list with **no `nextUpdate` at all is stale**, not current: RFC 5280 §5.1.2.5 makes the field optional and tells CAs to include it, and nothing asserts such a list is still good. `PKI_REASON_REVOKED` carries the revocation **date**, because a signature made before that instant may still be good and a caller deciding that needs the date. And a revocation found on a stale list from the wrong CA is **still reported** — hiding it behind an earlier failure is the one direction of error that matters.

  New probe, and a cost recorded rather than hidden: the CRL surface measures 52 KB because it reaches the x509 extension reader, whose decoder map references all twenty certificate-extension decoders so none can be tree-shaken. A caller who reads only CRLs pays for decoders a CRL never uses. The trade was taken deliberately — an `authorityKeyIdentifier` on a CRL decoded properly is worth more to almost every caller than the 35 KB they would save — and the reason is written next to the budget.
- **feat(revocation): RFC 5280 CRLs, walked rather than decoded** — `parseCertificateList` reads the envelope and `findRevocation` answers about one serial. There is **no array of entries**, and that is the design rather than an omission: a CRL entry costs three ASN.1 nodes, so decoding the list into a tree hits `maxNodes` (200 000) at roughly 65 000 entries, while `maxInputBytes` would allow millions and real CRLs sit in between. Exposing an array would either cap the library below real-world sizes or allocate hundreds of megabytes to answer one yes-or-no. So the envelope is decoded — it is small and every field matters — and the list is **walked** with a new lazy TLV cursor, one header at a time, in constant memory, bounded by the new `maxRevokedCertificates` (1 000 000, CWE-400). A test walks 100 000 entries, which `maxNodes` would refuse outright.

  The cursor (`src/asn1/asn1-cursor.ts`) is a **second reading path over attacker-controlled bytes**, so it is strict in every place the decoder is strict — indefinite length, non-minimal length, non-minimal high tag, a child overrunning its parent — because a cursor that accepted what the decoder refuses would be a weaker parser for the same input, which is the ambiguity DER exists to remove. Its own suite tests every refusal.

  Serials are compared **by content octets, never by `value`**: two serials differing only in a leading zero octet are two serials to a CA, and comparing the `bigint` would make them one — a revocation silently missed. A `cRLReason` nobody can read leaves `reason` undefined rather than inventing one, and never hides the entry: a hidden revocation is the worse failure. Code 7 is unassigned in RFC 5280 §5.3.1 and stays undefined. `crlNumber` and `isDelta` are read, because a **delta CRL is not a full one** and treating it as complete would report every certificate absent from it as unrevoked.

  Writing the tests found a real defect: the parser inferred whether the OPTIONAL `version` field was present from its *value*, so a CRL spelling v1 out as `0` had its `signature` read one field too early. The index is now carried out of the walk that found it.
- **feat(path): the certificate policy tree, and a data structure that makes it tractable** — the `valid_policy_tree` of RFC 5280 §6.1 is the hardest part of the specification, and most of the difficulty is in the representation rather than the rules. This one is **flat levels, children by index, no parent pointers, and nothing ever removed — only marked dead.** That single decision makes the three operations that break naive designs each a few lines: *"prune the nodes with no children"* is one backward pass, because a node's children are right there as indices and a dead child is just a dead entry; *"the nodes at depth i"* is `levels[i]`; and `maxPolicyNodes` (new, 4 096, CWE-770) is a counter over live entries, checked where they are created. A design that spliced nodes out of arrays would invalidate every index it had just handed out — marking instead of compacting costs a boolean and buys stable indices for the whole walk. What the module deliberately does *not* do is interpret a qualifier: a CPS URI or a user notice is carried through because §6.1.5 (b) returns it, and acting on one would be inventing policy.

  `policyMappings`, `policyConstraints` and `inhibitAnyPolicy` are processed, so those four extensions leave the refused set: `PROCESSED_CRITICAL_EXTENSIONS` now covers every §6 input, and everything else critical — `cRLDistributionPoints` included, until revocation lands — is still `PKI_REASON_UNRECOGNISED_CRITICAL_EXTENSION`. Three behaviours worth knowing: a specific policy **may** descend from a parent that asserted `anyPolicy` (omitting that fallback refuses most real hierarchies); a mapped node is **deleted** rather than left alone when mapping is inhibited, which is §6.1.4 (b)(2) and the reading that refuses a CA renaming a policy after being told not to; and a self-issued certificate spends none of the three counters (§6.1.4 (h)), so a CA re-keying itself does not consume anyone's budget. `PKI_REASON_NO_VALID_POLICY` fires only where §6.1.5 (g) says it may — an empty tree with nobody requiring an explicit policy is not a failure, it means the question was never asked — and `PKI_REASON_POLICY_MAPPING_INVALID` reports a mapping naming `anyPolicy`, which is ignored rather than honoured.
- **feat(path): name constraints — the check whose absence is the classic cross-signing attack** — a CA constrained to `.example.com` issuing for `bank.example` and nobody noticing. RFC 5280 §6.1.4 (g) accumulates permitted and excluded subtrees walking **down** the path; §6.1.3 (b) and (c) test each certificate against what accumulated above it, on the **subject as well as the SAN** — testing only the SAN lets a constrained CA issue for a CN nobody checked, and testing only the subject misses every modern certificate. Five name forms: dNSName, rfc822Name, uniformResourceIdentifier, iPAddress and directoryName. Three design points carry the security: the state is **per name form**, because §6.1.4 (g)(1) intersects within a form and leaves the others alone, and one flat list gets the intersection wrong the moment two CAs constrain different forms; an **empty** permitted set means "nothing of this form is acceptable" while an **absent** one means "no opinion", and collapsing `[]` into `null` makes a validator either refuse everything or permit everything; and the intersection **narrows only** — a sub-CA cannot grant itself names its issuer withheld. Exclusion wins over permission, as §6.1.3 (c) requires, because checking permission first would let the order of two CAs' constraints decide the answer. Matching is textual and by suffix on a folded form, never through a URL parser: a validator that normalised hostnames would inherit whatever that parser thinks about trailing dots, IDNA and userinfo, which is how name-constraint bypasses get written. The test table is mostly negatives, each one a certificate a permissive implementation accepts — `example.com` must not match `notexample.com`, a dotted constraint must not match the bare name, a width mismatch between IPv4 and IPv6 is not a match, and a URI whose host cannot be found is refused rather than accepted. Writing them found a real defect: the port after an IPv6 literal was not stripped, so `[2001:db8::1]:443` was compared as a host.
- **feat(path): RFC 5280 §6, and a validator that refuses what it does not yet understand** — `validateCertificatePath` takes a chain, trust anchors, an instant and **signature verdicts computed beforehand**, and returns a report. That input shape is the design: putting `subtle.verify` inside §6 would make the whole state machine asynchronous, unfuzzable without a host, and would mix an I/O-shaped failure with a logical one. Instead it is **synchronous**, **pure**, and the signatures get checked in parallel before the walk — `verify-bundle` weighs the claim at 7.4 KB with no Web Crypto bridge, no ASN.1 decoder, no registry and no hashes retained. It **never throws** for a validation issue: an empty chain, no trust anchor and no verdicts are each an answer. And it reports **every** applicable reason rather than the first, because a caller fixing one problem per round trip is a caller the report failed. The layer is a mutable state record plus exported pure step functions — the shape `Asn1Context` already uses — so a PKITS case becomes a three-line test against a synthetic `PathState` instead of a whole chain; a closure factory would have hidden the state and left the steps reachable one way only.

  **What it refuses rather than ignores.** §6.1.3 (f) requires a verifier to refuse a critical extension it does not process, and `nameConstraints`, `policyConstraints`, `policyMappings` and `inhibitAnyPolicy` are not in `PROCESSED_CRITICAL_EXTENSIONS` yet — so a chain relying on any of them comes back `PKI_REASON_UNRECOGNISED_CRITICAL_EXTENSION`. That is the correct answer and what makes finishing §6 in stages safe: a validator that ignored a constraint it had not implemented would answer "valid" for a chain the issuing CA forbade, which is the shape of a CVE rather than a missing feature.

  Writing the tests against the real Let's Encrypt hierarchy found two defects that no synthetic chain would have shown. **Path-length accounting ran the wrong way**: §6.1.4 (l) and (m) count *downwards from the anchor*, and walking leaf-to-root made a CA's own `pathLenConstraint` apply to its issuer — which refuses every chain under a `pathLenConstraint: 0` intermediate, meaning essentially all of Let's Encrypt. And **the trust anchor was required to be in the chain**, where §6.1.1 (a) takes it as a separate input — which refuses the leaf-plus-intermediate presentation most servers actually send. New named limit `maxChainLength` (10, CWE-400), reported as `PKI_REASON_LIMIT_EXCEEDED` rather than thrown, because reaching a bound while judging a chain is an answer about that chain.
- **feat(core): `PkiReasonCode`, the third vocabulary — landed before the code that needs it, on purpose** — a validation answers a different question from a parser, and neither existing registry can carry it. A validation produces *several* reasons at once (expired **and** revoked **and** outside a name constraint) where an exception carries one; the error vocabulary freezes at 0.8 while validation reasons grow with the standards; and on the diagnostics side the severity model is wrong for a verdict, with `strict: true` turning "this certificate is revoked" into a thrown `PKI_STRICT_DIAGNOSTIC`. So: `PkiReasonCode` and `PkiReason` in `src/types/pki-reasons.ts`, one factory per code in `src/core/pki-reasons.ts`, the registry in `docs/data/reasons.json`, and the rule this establishes for everything after it — **primitives return and throw, compositions report, exactly one layer converts.** The piece that makes it affordable is `PKI_REASON_INPUT_MALFORMED`, which carries in `errorCode` the `PkiErrorCode` that *would* have been thrown: a report promises never to throw for a malformed input **without copying 47 encoding codes into a second vocabulary** that would then have to be frozen too. The reason registry wraps the error registry; it never mirrors it. `reason-parity` holds all of it: bidirectional sync, a factory per code, the three registries disjoint, no `PKI_REASON_*` inside a `throw`, and no reason message starting with `pkinative: ` — the *inverse* of the error rule, because that prefix marks what is thrown and keeping it exclusive is what lets a log reader tell a verdict from an exception. Both of those last two checks are decided from the syntax tree rather than from the text: the first draft scanned the source with a regex and failed on this module's own explanation of itself, and on a `.replace(/^pkinative: /, '')` that strips the prefix rather than adding one.

  This is 0.5's first commit and it contains no validation logic at all. Taken late, it is the irrecoverable decision of the whole programme: 0.5 would ship path failures as error codes, 0.7 and pdfnative's migration would be built on `try/catch`, the x509-limbo scorer would score on exception codes, and 0.9 would have to choose between freezing wrong codes forever and breaking every consumer three months before 1.0.

## [0.4.0] – 2026-09-25

### Added

- **feat(conformance): the write direction — foreign tools reading what pkinative writes** — every conformance level so far points one way: bytes someone else produced, read by pkinative. From 0.3 the arrow points outward too, and that direction has **no corpus**: nobody publishes a set of certificates a library is supposed to have written, so the only oracle is the tools themselves. `npm run interop` hands each artefact of the sample catalogue — the same bytes `verify:samples` freezes by hash, so a baseline and a matrix cannot each be green about something the other never saw — to every tool it can find, and requires agreement on the serial as an integer, the subject common name, the DNS names, whether the chain verifies and whether the request's self-signature checks out. OpenSSL 4.0.0 and Windows CryptoAPI agree on all of it. Three design points decide whether that means anything: a tool **refusing** an artefact is a finding about pkinative (the opposite of the read direction, where a stricter foreign policy is not our defect); a tool this runner cannot **parse** is a defect in the runner and never evidence about the certificate; and each tool declares which fields it supplies, with a tool that compared nothing failing as vacuous. The second of those was found by the first run: Windows `certutil` reads the artefacts perfectly and prints "Numéro de série" on a French system, and a runner with two states reported a good certificate as refused — a gate that is red in one language and green in another. It now runs inside the `conformance` job, whose three contexts the ruleset already requires, so the matrix is blocking on Linux, Windows and macOS without the ruleset changing. The five tools not yet written are declared in `scripts/lib/interop.ts` with the reason each is pending, and `interop-matrix-declared` holds that list to ROADMAP.md in both directions, so a gap cannot quietly disappear from either side.
- **feat(conformance): level L5, RFC 5280 clause by clause — the gate stops being a regression detector** — L1 to L4 are all *differential*: they prove agreement, not correctness, and if pkinative, OpenSSL and `node:crypto` were wrong in the same way L3 would be green. A red L1 says "certificate `ab3f…` was refused and the baseline says otherwise". L5 says: *"RFC 5280 §4.2.1.9 is violated by 14 certificates of the corpus; pkinative diagnoses 13 and is silent on one."* That is a claim about **attribution**, and it is the property every other level lacks. `scripts/lib/clauses.ts` holds 19 clauses of §4.1 and §4.2, each quoting its normative sentence and naming the diagnostic that must report it; `scripts/validators/rfc5280-clauses.ts` decides each one from raw bytes without importing `src/`, because two readings that share a decoder cannot disagree. The runner fails on a violation pkinative is silent about, and — for a clause that claims to decide every case its diagnostic covers — on a diagnostic with no violation behind it. On the first run over 29 797 parsed certificates: 8 clauses violated across 15 readings, **every one attributed**, no silent miss and no phantom. Two clauses x509-limbo cannot reach (a unique identifier, a multi-valued RDN — neither bears on path validation) carry a reviewed waiver naming the suite that does exercise them, and `tests/conformance/clauses.test.ts` builds a violating and a conforming certificate for **every** clause, which is the only thing that could catch an evaluator that always answers "pass". The new `clause-table-complete` rule refuses a clause pointing at a diagnostic code that does not exist, a clause with neither a diagnostic nor a written waiver, a quote with no normative keyword in it, and a conformance guide that stops describing L5.
- **feat(build): `subjectAltName` can name an IP address and a registered ID** — the parser has modelled `iPAddress` since 0.1, with its version and its mask, and the encoder could not write one. That asymmetry is the defect: an IP SAN is routine, and a caller forced to hand-encode one is a caller getting IPv6 byte order wrong. It takes **bytes**, not text, for the same reason `issuerDer` does — `2001:db8::1` and `2001:0db8:0000:0000:0000:0000:0000:0001` are two spellings of one address, and a certificate that names the wrong host because a `::` expanded differently is not a bug anyone finds quickly. Four and sixteen octets only: the 8- and 32-octet forms carry a mask, belong to `nameConstraints`, and are refused here where they would mean nothing. `registeredID` comes with it, and the union is now the exported `GeneralNameDescription`.
- **feat(conformance): an output-byte baseline for what pkinative writes** — `scripts/verify-samples.ts` hashes 24 samples, from a single `AlgorithmIdentifier` to a signed certificate chain and a PKCS#10 request, against `scripts/data/output-bytes.json`, where every entry records the release its hash came from. L0–L4 ask whether pkinative *reads* bytes the way everyone else does and say nothing about the bytes it *writes*; an encoder can drift — a string type swapped, a `DEFAULT` emitted, a SET reordered — with every structural assertion still green, because the structure is still right. These are the bytes a relying party hashes. Signed samples use Ed25519, which RFC 8032 makes deterministic, from a fixed 32-octet seed wrapped in a PKCS#8 prefix in the script itself: nothing secret-looking is committed and "never commit what our own code can build" holds. Every signed sample was confronted with OpenSSL 4.0.0 before the baseline was blessed — `openssl verify` builds and checks the leaf against the root, `openssl req -verify` accepts the request, and all four SAN forms read back correctly.
- **feat(bench): a performance trend, and a rule that keeps it attributable** — `bench.yml` archives `npm run bench` weekly with the run context written into the artefact beside the numbers, because a number without its machine is not evidence and a reader six months later will not have the run page open. It is never a required check: a shared runner varies 2-5x run to run, so a blocking budget either fires false-red every week or is loose enough to miss a real regression, and both teach people to ignore it. There is deliberately no `continue-on-error: true` either — it blocks nothing already, so a green square over a crashed run would hide the one thing the workflow can still report, that the benchmarks stopped running at all. The 0.3 creation paths get benchmarks of their own, and the new `bench-parity` rule closes the three ways a performance record rots: two benchmarks may not share a name (every results table is keyed by name), every dated section of `bench/RESULTS.md` declares where its numbers came from or says in writing why the usual context does not apply, and the workflow must actually run `npm run bench` while never appearing among the ruleset's required contexts.

## [0.3.0] – 2026-09-24

### Added

- **feat(crypto): a certificate's signature can be verified, through Web Crypto and nowhere else** — `verifyCertificateSignature(certificate, issuer)` and `verifySelfSignature(certificate)` answer whether the issuer's key signed these bytes, over RSA PKCS#1 v1.5, RSASSA-PSS, ECDSA on P-256/384/521, Ed25519 and Ed448. `canVerify()` says whether the runtime can be asked at all. The new `crypto` layer imports **no `x509`**: everything a verifier needs is already on the parsed structure as data, so `verify-bundle` measures 12.7 KB with neither the parser, nor the ASN.1 decoder, nor the hashes in it — and the parser probe proves the converse, that reading a certificate ships no Web Crypto bridge. A layer diagram is a drawing until something weighs it.
- **feat(crypto): `PkiCryptoError`, and the line it draws** — a verification that runs returns a boolean; it throws only when it could not run. `PKI_CRYPTO_UNAVAILABLE`, `PKI_CRYPTO_ALGORITHM_UNSUPPORTED` and `PKI_CRYPTO_KEY_UNSUPPORTED` all mean "ask me again elsewhere", never "this certificate is bad". A malformed signature, an issuer key of the wrong family and two disagreeing `signatureAlgorithm` fields are each **`false`** — failing closed, so a caller who forgets a `catch` gets "not verified" rather than an exception a layer above may swallow into a success path. That distinction is what 0.9's non-throwing reports are built on, which is why the class exists now and not then.
- **feat(crypto): a strict DER ↔ P1363 signature converter** — X.509 carries ECDSA as `SEQUENCE { INTEGER r, INTEGER s }`, Web Crypto takes raw `r ‖ s`, and nothing bridges them for you. This one refuses a non-minimal INTEGER, a negative `r`, a two-octet length, a value wider than the curve and a third value hiding after the pair — every Wycheproof class that lets one signature be presented in several encodings (CWE-436). P-521 is 66 bytes, not 65.
- **feat(build): certificates and PKCS#10 requests, written from a typed description** — `createCertificate(description, signer)` and `createCertificationRequest(description, signer)` produce DER, signed by a key the caller holds. The `build` layer imports **no `x509`**, the same invariant as `crypto` from the other side, and `verify-bundle` weighs it: 17.2 KB for the whole builder with neither the parser, nor the ASN.1 decoder, nor the OID registry, nor the hashes in it — an application that only issues certificates does not pay for reading them. Every structure a test or a recipe builds is parsed straight back with `onDiagnostic` and **zero diagnostics** is the assertion, which is how the builder is held to the profile its own reader enforces. Six algorithms round-trip through OpenSSL 3.5.5 — ECDSA on P-256/384/521, RSA PKCS#1 v1.5, RSASSA-PSS and Ed25519 — each certificate and request read and verified by `openssl` before pkinative reads it again.
- **feat(build): the structural encoders, public, because the next structure is always one you do not model yet** — `encodeAlgorithmIdentifier`, `encodeDistinguishedName`, `encodeNameAttribute`, `encodeValidity`, `encodeSubjectPublicKeyInfo`, `encodeExtension`, `encodeExtensions` and `encodeAttribute`, plus value encoders for basicConstraints, keyUsage, extendedKeyUsage, subjectKeyIdentifier, authorityKeyIdentifier and subjectAltName. `encodeAlgorithmIdentifier` is where the classic silent failure lives: RSA requires an explicit `NULL` parameter and EC and Ed25519 require its absence, and getting that backwards produces a signature that verifies nowhere while every field still reads correctly. They live in `build/`, never in `asn1/`, because a certificate structure is not an ASN.1 primitive.
- **feat(asn1): the four encoders a structure needs and a primitive cannot give** — `encodeExplicit` wraps a complete TLV in a constructed context tag; `encodeImplicit` **replaces** a value's own tag, carrying its constructed bit across, which is what an ASN.1 module's `IMPLICIT` means and what a wrapper would silently get wrong (`[0] IMPLICIT SET OF` in a CSR's attributes is exactly that trap, and it decodes by accident when there is only one attribute). `encodeEnumerated` reaches tag 10, which a CRL's `reasonCode` requires and an INTEGER will not do for. `encodeNamedBits` takes bit numbers and applies X.690 §11.2.2 trailing-zero trimming, the encoding side of the `PKI_DIAG_NAMED_BITS_TRAILING_ZERO` diagnostic already emitted on the reading side.

- **feat(fuzz): coverage-guided fuzzing, with the engine outside the manifest** — three ClusterFuzzLite targets in `fuzz/`: the X.690 decoder in both rule sets, the RFC 5280 parser with and without extension decoding, and PEM together with the OID codec — the last asserting `encodeOid(decodeOid(x))` byte for byte, because a round trip that loses an arc is silent data loss no error class would ever report. Jazzer.js is installed inside the build image with `--no-save` and never in `package.json`, so the zero-dependency promise is a property of what a consumer installs and stays checkable. The seed corpus is the committed CA roots: starting a DER fuzzer from random bytes spends days rediscovering the tag-length header. The workflow is non-blocking **by construction** — the ruleset lists the seven contexts that block a merge and this is not one — rather than by a `continue-on-error:` that would hide a red run. `tests/fuzzing/targets.test.ts` runs the same three files against `src/` on every gate: it proves they load, survive every truncation and mutation of a seeded corpus, and still **rethrow** what is not a `PkiError`, which is asserted by planting a `TypeError` in a mocked library — a target widened to `catch {}` would fuzz for a week, crash on nothing and report success. The container wiring itself has never executed and SECURITY.md says so until it has.

### Changed

- **`KEY_OPERATION_POLICY` replaces the blanket key-operation ban** — the old rule refused eleven Web Crypto operations everywhere in `src/`, including in a *type declaration*, so 0.3 could not have declared its own host types. Deleting entries would have traded the guarantee for the feature; instead each operation now lists the exact modules allowed to name it. `importKey`, `verify` and `sign` are allowed in two files; `generateKey`, `exportKey`, `deriveBits`, `encrypt` and `wrapKey` are refused **in every version**, and three more until 0.8 opens PKCS#8 and PKCS#12 under PBES2. `globalThis.crypto` gains the same treatment `console` already had: one door, two modules. The table is in SECURITY.md and held to the code by the new `key-operation-parity` rule, because prose stating the project's central security promise must not be able to drift from the check that gives it.
- **`exportKey` being refused forever has an API consequence, and it is the right one** — a caller hands the builder a SubjectPublicKeyInfo in DER rather than a `CryptoKey`. One line in their code, in exchange for a promise a test can check.
- **`type-surface-parity`, so a declaration budget cannot be raised quietly** — `dist/index.d.ts` has the least headroom of anything pkinative ships and it crossed its budget here. Bytes drift with TSDoc wording, so `declared.typeSurface` now records the counts that actually decide the weight: 95 exported types, 70 values. Subpath exports are revisited at 1.0 if the file passes 200 000 bytes.

- **feat(governance): the body of a release pull request becomes part of the record** — `release-notes/draft/PR-vX.Y.Z.md`, **committed**, one per release, scaffolded by `release-prepare.ts` from `release-notes/PR_TEMPLATE.md` alongside the release note.
