# pkinative v0.3.0

> This version was tagged, never released: the install instructions below describe a release that was not made.

<!-- GitHub Release title: v0.3.0 — write certificates, check signatures, hold no key -->

_Released 2026-09-24_

Milestone M2. pkinative stops being a reading library: it verifies a certificate's signature against its issuer, and it builds and signs certificates and PKCS#10 requests from typed descriptions. Both go through Web Crypto and nothing else — `generateKey` and `exportKey` stay refused inside `src/` in every version, so the key belongs to the caller and the promise is checkable rather than stated. Additive for anyone on v0.2.0: no export was removed or renamed, and no parsing behaviour changed.

## Highlights

- **Verification** — `verifyCertificateSignature`, `verifySelfSignature`, `canVerify`, over RSA PKCS#1 v1.5, RSASSA-PSS, ECDSA on P-256/384/521, Ed25519 and Ed448.
- **Creation** — `createCertificate`, `createCertificationRequest`, `canSign`, plus fifteen structural encoders for the structure this library does not model yet.
- **The layer diagram, weighed on the artefact** — neither `crypto` nor `build` imports `x509`. `verify-bundle` measures 12.7 KB for the verifier and 17.2 KB for the whole builder, each with no parser, no ASN.1 decoder, no OID registry and no hashes in it.
- **Coverage-guided fuzzing** — three ClusterFuzzLite targets, with Jazzer.js installed inside the build image and never in `package.json`.

## Added

- **feat(crypto):** `verifyCertificateSignature(certificate, issuer)` and `verifySelfSignature(certificate)` answer whether a key signed these bytes. `canVerify()` says whether the runtime can be asked at all. The `crypto` layer imports no `x509`: everything a verifier needs is already on the parsed structure as data.
- **feat(crypto):** `PkiCryptoError` with `PKI_CRYPTO_UNAVAILABLE`, `PKI_CRYPTO_ALGORITHM_UNSUPPORTED` and `PKI_CRYPTO_KEY_UNSUPPORTED`. A verification that runs returns a boolean; it throws only when it could not run. A malformed signature, an issuer key of the wrong family and two disagreeing `signatureAlgorithm` fields are each **`false`**, failing closed.
- **feat(crypto):** a strict DER ↔ P1363 converter, refusing a non-minimal INTEGER, a negative `r`, a two-octet length, a value wider than the curve and a third value hiding after the pair — every Wycheproof class that lets one signature be presented in several encodings (CWE-436).
- **feat(build):** `createCertificate` and `createCertificationRequest`, signed by a key the caller holds. Six algorithms round-trip through OpenSSL 3.5.5: each certificate and request is read and verified by `openssl` before pkinative reads it again.
- **feat(build):** the structural encoders — `encodeAlgorithmIdentifier`, `encodeDistinguishedName`, `encodeNameAttribute`, `encodeValidity`, `encodeSubjectPublicKeyInfo`, `encodeExtension`, `encodeExtensions`, `encodeAttribute`, and value encoders for six extensions. `encodeAlgorithmIdentifier` is where the classic silent failure lives: RSA requires an explicit `NULL` parameter, EC and Ed25519 require its absence, and getting it backwards signs something that verifies nowhere while every field still reads correctly.
- **feat(asn1):** `encodeExplicit`, `encodeImplicit`, `encodeEnumerated`, `encodeNamedBits`. `encodeImplicit` replaces a value's tag and carries its constructed bit across, which is what an ASN.1 module's `IMPLICIT` means; a wrapper decodes by accident when a CSR carries one attribute and breaks on two.
- **feat(fuzz):** ClusterFuzzLite over three targets, non-blocking by construction rather than by a `continue-on-error:`. The PEM target also asserts `encodeOid(decodeOid(x))` byte for byte.

## Changed

- **refactor(tools):** `KEY_OPERATION_POLICY` replaces the blanket ban on eleven Web Crypto operations. The old rule refused them everywhere in `src/`, including in a type declaration, so 0.3 could not have declared its own host types. Each operation now lists the exact modules allowed to name it; `generateKey`, `exportKey`, `deriveBits`, `encrypt` and `wrapKey` are refused in every version. SECURITY.md carries the table and `key-operation-parity` holds the prose to the code.
- **refactor(docs):** `declared.typeSurface` records 95 exported types and 70 values. A byte budget on `dist/index.d.ts` drifts with TSDoc wording and can be raised without anyone noticing the surface doubled; these two counts cannot change by accident.
- **chore(build):** the `dist/` byte budgets were raised once for this milestone, measured in the release commit: 188455/190308/109647/109647/535650/535653. The declaration files grew 36 % against 11 % for the code.

## Fixed

- **fix(governance):** the human-in-the-loop guard was wired to `Bash` alone. On Windows, where PowerShell is the primary shell, a hook that is never invoked parses nothing. Both halves are now written once per shell tool and `agent-config-parity` fails on a tool missing either.
- **fix(ci):** harden-runner is skipped on macOS, with the reason in the file. The action does not support macOS; the repository carried a comment asserting it "records that the platform is unsupported and continues", which was an untested claim.
- **fix(tools):** the architecture checker crashed on a property named `toString` — true through the prototype chain, and a function where a list was expected. The same hazard the engine's own "no object keys from input" rule exists for (CWE-1321).

## Performance

No measured change to the parsing path; nothing in `crypto` or `build` is reachable from `parseCertificate`. A performance trend lands in 0.4.0 (`bench.yml`), and no number is quoted here that a command did not produce.

## Conformance

Corpus pins are unchanged: x509-limbo at `1187213`, 9 793 test cases over 30 361 certificates, 564 reviewed refusals; Wycheproof at `3fa63dd`, 1 530 vectors. L4 still has one validator, Microsoft CryptoAPI. The interoperability matrix and the clause checker (L5) are 0.4.0, and the write direction of that matrix was impossible before this release created anything.

## Documentation

- **docs(guides):** `use-cases.md` grows a sixth job, issuing a certificate, and loses the row that promised it. `recipes/create-certificate.ts` builds a root, a leaf it signs and a request, and `recipes/asn1-primitives.ts` gains the EXPLICIT/IMPLICIT contrast — 10 executable recipes, each asserted on every test run.
- **docs(security):** SECURITY.md gains the key-operation table and the fuzzing section, including the note that the container has never executed.

## Known limitations

- **No chain is validated.** A verified signature proves one key signed one set of bytes. Trust needs a trust anchor, a validity window, name constraints, policies and revocation — RFC 5280 §6, which is 0.5.0.
- **Ed448 and, on several runtimes, Ed25519 are not implemented by the host.** `canVerify()` returning `true` says the runtime has Web Crypto, not which algorithms it has; an unsupported one is `PKI_CRYPTO_KEY_UNSUPPORTED`, never `false`.
- **The ClusterFuzzLite workflow has never run.** This repository has no pushed history. The targets are proved locally against `src/`; the container wiring is not proved at all, and SECURITY.md says so until the first scheduled run.
- **No CRL, no OCSP, no CMS, no PKCS#8 or PKCS#12.** 0.5.0, 0.7.0 and 0.8.0 respectively.

## Downstream integration notes

Everything below is additive; nothing was removed or renamed.

- **New error class and codes.** `PkiCryptoError`, with `PKI_CRYPTO_UNAVAILABLE`, `PKI_CRYPTO_ALGORITHM_UNSUPPORTED` and `PKI_CRYPTO_KEY_UNSUPPORTED`. A consumer switching on `PkiErrorCode` must handle three more values. They mean "could not check", never "the certificate is bad".
- **27 new runtime exports, 11 new types, nothing removed** — 127 exports become 165, counted by diffing `docs/assets/api.json` against the v0.2.0 tree. The runtime additions: `KEY_USAGE_BITS`, `PkiCryptoError`, `canSign`, `canVerify`, `createCertificate`, `createCertificationRequest`, `encodeAlgorithmIdentifier`, `encodeAttribute`, `encodeAuthorityKeyIdentifier`, `encodeBasicConstraints`, `encodeDistinguishedName`, `encodeEnumerated`, `encodeExplicit`, `encodeExtendedKeyUsage`, `encodeExtension`, `encodeExtensions`, `encodeImplicit`, `encodeKeyUsage`, `encodeNameAttribute`, `encodeNamedBits`, `encodeSubjectAltName`, `encodeSubjectKeyIdentifier`, `encodeSubjectPublicKeyInfo`, `encodeValidity`, `signatureAlgorithmDer`, `verifyCertificateSignature`, `verifySelfSignature`. The types: `CertificateDescription`, `CertificationRequestDescription`, `CreateOptions`, `ExtensionDescription`, `NameAttribute`, `NameDescription`, `PkiCryptoErrorCode`, `SignatureAlgorithm`, `SignatureHash`, `SigningKey`, `VerifyCertificateSignatureOptions`.
- **`subjectPublicKey` takes SubjectPublicKeyInfo DER, not a `CryptoKey`.** `exportKey` is refused inside `src/` in every version, so extracting the public half is one line in your code: `new Uint8Array(await crypto.subtle.exportKey('spki', publicKey))`. An API that hid that line would make the central security claim unverifiable.
- **`serialNumber` as bytes is now validated.** An empty or non-minimal value throws `PKI_API_MISUSE` instead of producing a certificate pkinative's own decoder refuses. A negative serial in that form is still written — the byte form exists to reproduce an existing serial exactly — and comes back as `PKI_DIAG_SERIAL_NOT_POSITIVE` on read.
- **The `build` and `crypto` layers are registered in `LAYERS`.** Neither may import `x509`, and `verify-bundle` proves it on the built artefact rather than in review.
- **For pdfnative.** The PAdES/LTV stack's migration target is CMS, which is 0.7.0. What is usable now is signature verification against an issuer, and `createCertificationRequest` for the enrolment path.
