# pkinative v1.0.0

<!-- GitHub Release title: v1.0.0 — the freeze, promised -->

_Released 2026-10-04_

Milestone M6, and the first release of pkinative: on npm with provenance, and on GitHub with attested assets. Versions 0.1 to 0.9 were git tags only, never released, so nothing needs migrating unless you built from one of them. 1.0.0 was to add no feature over 0.9.0; before the first publication it took every item its 1.1 list held (see Highlights), so that the first release is complete rather than followed by a minor three weeks later. What it adds above all is a promise: for the whole 1.x line, the export surface, the error vocabulary and the decision surface (which certificates pkinative refuses, and with which code) change only in ways semantic versioning allows, each recorded in a committed snapshot and held by a rule that fails the build. Before making it, a pre-publication audit — nine independent auditors, each checked by an adversarial verifier — confirmed 98 findings; every one is fixed or decided below, because what 1.0 ships it cannot take back. **From a 0.9.0 build, read Upgrade: `openPkcs12` needs `rsaAlgorithm` for RSA keys, and name attributes are now written in the string type RFC 5280 gives them.**

## Highlights

- **The compatibility promise, in three parts.** [SECURITY.md §Compatibility promise](../SECURITY.md#compatibility-promise) states what 1.x keeps, and `ecosystem.json → contracts.compatibility` states it for machines:
  - **The export surface.** Every export keeps its name, its kind and a compatible signature, and every `PkiReasonCode` stays. Held by `docs/assets/api.frozen.json` and the `api-surface-frozen` rule.
  - **The error vocabulary.** The 57 `PkiErrorCode`s keep their names and classes, as they have since 0.8.0. Held by `docs/data/errors.frozen.json` and `error-codes-frozen`.
  - **The decision surface.** Each of the 565 x509-limbo certificates pkinative refuses stays refused with the same code; a new refusal is a recorded fix; every corpus certificate re-encodes byte for byte. Held by `docs/data/refusals.frozen.json`, `refusal-baseline-frozen` and conformance levels L1 and L2 ([ADR 0014](../docs/adr/0014-the-decision-surface-contract.md)).
  - **Beyond the snapshots** ([ADR 0018](../docs/adr/0018-what-the-1-x-promise-covers-beyond-its-snapshots.md)): every option default and the direction a minor may move it (`docs/data/defaults.json`, held by `option-defaults-parity`), verdicts recorded but not frozen, returned unions open, and what is not promised, written down.
- **The decisions 1.0 could not leave open.** One entry point for 1.x: no subpath export, a later minor may add one ([ADR 0016](../docs/adr/0016-one-entry-point-for-1-x.md)). A runtime and toolchain policy: Node.js LTS lines at a patched floor, TypeScript 5.0 compiled for real at release, ES2020 ([ADR 0017](../docs/adr/0017-runtime-and-toolchain-support.md)). Error identity across the ESM and CJS builds ([ADR 0021](../docs/adr/0021-error-identity-across-builds.md)).
- **The 1.1 list, pulled in before the first publication (2026-10-03).** Everything ROADMAP.md §1.1.x held was to wait for a minor, because each item would have widened the frozen surface without a rehearsal. An unpublished 1.0 that is complete beats a 1.1 three weeks later — nobody yet depends on the surface being frozen, and a minor weeks after the first release says the first release was not finished — so each item landed under the bar every release already clears: the publish gate, the interoperability matrix with `--require-all`, 100 % mutation on every module it touched, a fuzz target per new reader, frozen samples for every writer, and `api.frozen.json` ratcheted after each lot so that every addition is promised at 1.0.0 ([ADR 0018](../docs/adr/0018-what-the-1-x-promise-covers-beyond-its-snapshots.md)). The items: a PKCS#10 reader and verdict; signatures verified lazily inside `verifyCertificateChain`; the fourteen RFC 5652, 3161 and 6960 sentences recorded as not diagnosed, now thirteen diagnostics; id-RSASSA-PSS keys verified by re-wrapping at the Web Crypto door; Ed448 CMS signers verified where the host verifies Ed448, with SHAKE256 computed here ([ADR 0022](../docs/adr/0022-ed448-cms-signers-host-dependent.md)); an OCSP delegate judged at `producedAt`; the ENUMERATED and RELATIVE-OID readers; the X.520 upper bounds and ISO 3166-1 as diagnostics; the surface classifier, `schemaVersion`, the compiled guides, the accessibility job and Node.js 26 on an advisory run. Each is listed under Added and Changed below.
- **Security fixes found before anyone could depend on the defect** — see Security.
- **Cross-validated against the tools people use.** What pkinative writes is read by eight foreign implementations on every conformance run — OpenSSL, GnuTLS, gpgsm, .NET, Java, Python cryptography, Go and Windows CryptoAPI — and five of them (OpenSSL, GnuTLS, gpgsm, .NET and Windows CryptoAPI) also write the signed messages, timestamps, OCSP responses, CRLs and key containers pkinative reads back; Java, Python cryptography and Go only read. The X.509 linters zlint and pkilint report no error on any certificate pkinative creates, except where the linter itself is wrong — a raw-octet scan of a BMPString name, an RSA-PSS signature pkilint cannot verify — each such case proved and recorded in `TOOL_LIMITATIONS`.
- **The release path hardened before its first use** ([ADR 0019](../docs/adr/0019-release-integrity-slsa-build-l2.md)): the job that runs the build cannot publish, the job that publishes runs nothing from the repository and uploads exactly the tarball the build handed on, and the attested tarball is the one fetched back from the registry. SLSA Build L2, said as such.

## Security

- **fix(keys): the PBKDF2 work of a whole PKCS#12 is bounded** (CWE-400; the class of CVE-2022-36083). `maxKdfIterations` bounded each derivation, not their number: a 544-byte file made `openPkcs12` run 34 s. The new limit `maxPkcs12KdfIterations` (10 000 000 by default, every real file from OpenSSL, .NET, Java, GnuTLS and pyca well under it) is charged before any derivation runs ([ADR 0020](../docs/adr/0020-a-kdf-budget-per-pkcs12.md)).
- **fix(revocation): `PKI_REASON_REVOKED` only from authenticated, applicable evidence.** A CRL from another issuer, out of scope or unverified, or an OCSP answer whose signature or responder authority failed, no longer reports a certificate revoked; an unauthenticated claim is carried in `PKI_REASON_REVOCATION_UNKNOWN` instead.
- **fix(path): name constraints that could be bypassed** (CWE-295, CWE-436): a URI host is read by the RFC 3986 grammar, so a backslash, a `%` or a second `@` no longer slips past a subtree; an SmtpUTF8Mailbox (RFC 9598) is held to rfc822Name constraints, as OpenSSL holds it; the opt-in commonName fallback of `checkServerName` is held to the path's dNSName constraints (new optional `path`), and refuses without it.
- **fix(crypto): id-RSASSA-PSS keys held to RFC 4055 §1.2 and §3.3**: a PKCS#1 v1.5 signature, or PSS parameters the key forbids, no longer verify under such a key.
- **fix(path): a trust anchor is a name and a key** (RFC 5280 §6.1.1 (d); CWE-295, CWE-347). A self-signed certificate copying an anchor's name, placed in the bag, ended the walk as the anchor with no signature checked — a bypass of chain validation open to whoever sends the chain. It is now one more link, whose signature the anchor it names has to vouch for.
- **fix(verify): a CRL issuer off the path is believed only once its own certificate validates under the same anchors** (§6.3.3 (f); CWE-295). A forged delta list hid an authenticated revocation and a forged complete list satisfied `requireRevocation`, both signed by a certificate the sender put in the bag. An indirect CRL issuer (§5.2.5) is validated with its own links.
- **fix(path): `user-initial-policy-set` is intersected in the anchor's domain** (§6.1.5 (g)(iii)), across policy mappings: the leaf-domain intersection accepted the policy nobody asked for and refused the one the user named (NIST PKITS 4.10.1).
- **fix(crypto): an RSA public exponent below 3 or even is refused before the key reaches Web Crypto** (RFC 8017 §3.1; CWE-347): Node.js imports e = 1 and verified a signature made with no private key. Diagnosed at parse as `PKI_DIAG_SPKI_RSA_EXPONENT_WEAK`.
- **fix(verify): a timestamp token stamping a SHA-1 imprint is not evidence without `allowSha1`**, as the request writer already refused to ask for one.
- **fix(keys): a PBMAC1 key shorter than 20 octets is a MAC this reader does not verify**: the length sits in the unauthenticated MacData, and at one octet the MAC was forged in 256 guesses.
- **fix(build): an ECDSA signing key without its curve is refused** (`PKI_INVALID_OPTION`; found by the final review of 2026-10-04). The type requires `namedCurve`; a JavaScript caller, or a cast, could omit it, and `createCertificate`, `createCertificationRequest` and `createSignedData` then wrote the host's raw r‖s where DER was expected — a well-formed artefact whose signature verifies `false` everywhere. `resolveSigner` now refuses a curve outside P-256, P-384 and P-521 before anything is signed.
- **fix(revocation): the CRL and OCSP readers are bounded like every other reader** (CWE-400; found by the second review of 2026-10-04). `parseCertificateList`, `findRevocation` and `parseOcspResponse` walk the root from the raw buffer with the cursor rather than through the node decoder, and consulted neither `maxInputBytes` nor a count: a root SEQUENCE of millions of two-octet values — 65 MiB — was materialised header by header, forty seconds and three gigabytes per reader, reachable through the `crls` and `ocspResponses` of `verifyCertificateChain`, where `parseCertificate` refused the same bytes in 400 ms. The input size is now the first refusal (`PKI_LIMIT_EXCEEDED`, `maxInputBytes`), and every walk stops at the field's own arity (`PKI_X509_STRUCTURE_INVALID`); a time budget holds both readers to the same second as the decoder.
- **fix(verify, build, revocation, hash): the minors of the second review of 2026-10-04.** The chain report keyed its "first of each list" set by the hex of every `crls`/`ocspResponses` entry before any reader saw it (1.8 GiB of strings for a 32 MiB input; CWE-400) — lists are now compared byte for byte. The writers hold every caller-supplied value to its shape before a signature is produced: `createCertificate` and `createCertificationRequest` refuse a `subjectPublicKey` that is not one SEQUENCE, `encodeExtension` a value that is not one DER value, an `ExternalSigner` for Ed25519 or Ed448 a signature that is not 64 or 114 octets (RFC 8032), and `createOcspRequest` a nonce outside 1 to 32 octets (RFC 8954 §2.1) — all `PKI_API_MISUSE`. `shake256` caps `outputLength` at 1 048 576 octets and `checkOcspStatus` refuses a `NaN` or negative tolerance — both `PKI_INVALID_OPTION`, where a `RangeError` or a silently disabled check stood.
- **fix(path, revocation): the decision minors of the final review** — version 1 and 2 intermediates are refused (§6.1.4 (k)); a `dns` reference that spells an IP address is compared with iPAddress entries only (RFC 2818 §3.1); an unknown critical CRL entry extension makes the list unusable (§5.3); an OCSP answer without `nextUpdate` is stale by default and two answers about one CertID that disagree are `PKI_REASON_REVOCATION_UNKNOWN`; a delegated OCSP responder is checked for revocation unless it carries `id-pkix-ocsp-nocheck`; the §6.3.3 reasons mask intersects the certificate's own distribution-point reasons; the implicit anchor counts against `maxChainLength`.
- **fix(asn1, crypto): two parser differentials closed** (CWE-436): the cursor the CRL and OCSP readers use refuses what the decoder refuses (the high-tag form below 31, tag 0, a primitive walked as constructed), an indefinite child is bounded by its definite parent, and RSASSA-PSS parameters are held to their grammar — each field once, in order, hash parameters absent or NULL.
- **A CVE-class corpus**: `tests/security/cve-classes.test.ts` replays the class of 43 published vulnerabilities of comparable PKI libraries — node-forge, jsrsasign, elliptic, OpenSSL, Go, Bouncy Castle, Java — every identifier checked against NVD or the GitHub Advisory Database, and `docs/data/cve-classes.json` says for each who stops it: pkinative, or the host's Web Crypto. No dependency, development ones included, has a known advisory at release (`npm audit`, `osv-scanner`).

## Breaking Changes

Breaking only against a 0.9.0 build of the tag, which was never published:

- **BREAKING: `openPkcs12` opens an RSA key only with the scheme you name** ([ADR 0015](../docs/adr/0015-no-default-rsa-scheme.md)). Without `options.rsaAlgorithm` the key stays closed and the report carries the new reason `PKI_REASON_PKCS12_RSA_SCHEME_UNSPECIFIED`.
- **BREAKING: name attributes are written in the string type RFC 5280 Appendix A gives them.** `countryName`, `serialNumber` and `dnQualifier` default to PrintableString, `domainComponent` and `emailAddress` to IA5String; a `stringType` the syntax excludes, or a value outside its bounds (`countryName` exactly two characters, `commonName` at most 64), is refused with `PKI_API_MISUSE`. pkilint rejected the old UTF8String countryName as a fatal syntax error.
- **BREAKING: `checkServerName`'s commonName fallback needs `path`** to hold the name to the issuing CAs' constraints, and refuses with `PKI_REASON_NAME_MISMATCH` without it.

## Added

- **feat(cms, revocation, verify): the fourteen RFC 5652, 3161 and 6960 requirement sentences recorded as `not-diagnosed` are diagnosed**, thirteen codes for fourteen sentences — a signer-less SignedData whose content is not the certificates-only form (`PKI_DIAG_CMS_CERTS_ONLY_CONTENT`); a countersignature's signed attributes looked into as far as RFC 5652 §11.4 asks (`PKI_DIAG_CMS_COUNTERSIGNATURE_CONTENT_TYPE`, `PKI_DIAG_CMS_COUNTERSIGNATURE_NO_MESSAGE_DIGEST`, `PKI_DIAG_CMS_COUNTERSIGNATURE_EMPTY`); a signingTime in GeneralizedTime for 1950–2049 or with fractional seconds (`PKI_DIAG_CMS_SIGNING_TIME_NOT_UTC`, `PKI_DIAG_CMS_SIGNING_TIME_FRACTION`); the certReq contract between a request and its token, decided where the two meet (`PKI_DIAG_TSP_CERTREQ_UNMET`, `PKI_DIAG_TSP_CERTS_UNREQUESTED`); what an OCSP response says about itself (`PKI_DIAG_OCSP_CERTS_EMPTY`, `PKI_DIAG_OCSP_VERSION_NOT_V1`) and against the signer that `checkOcspStatus` is now given (`PKI_DIAG_OCSP_RESPONDER_ID_MISMATCH`, `PKI_DIAG_OCSP_NOCHECK_CRITICAL`, `PKI_DIAG_OCSP_SINGLE_RESPONSE_UNREQUESTED`). ## Changed

- **fix(build):** RSASSA-PSS AlgorithmIdentifiers carry an explicit NULL after the hash and MGF1 hash OIDs, the CA/Browser Forum exact encoding; pyca's WebPKI verifier and zlint refused the absent form.
- **fix(asn1):** X.690 §8.23 violations in the ISO/IEC 10646 string types are diagnosed instead of silently accepted; the BER GeneralizedTime refusal names pkinative's subset.
- **fix(verify):** a revocation list's reason path is `crls[n]`, the input member it points at; a timestamp's `earliest` and `latest` are whole milliseconds, rounded outward.
- **fix(build):** `KEY_USAGE_BITS` is read-only at runtime.
- **fix(build):** `addTimeStampToken` takes a token made in another realm (a `vm` context, an iframe) as every other byte argument is taken; an `instanceof` test refused it with `PKI_INVALID_INPUT`. Found by the mutation pass.
- **fix(cms):** a TSTInfo extension whose `extnValue` is not an OCTET STRING is refused with `PKI_CMS_STRUCTURE_INVALID` at `TSTInfo.extensions[n].extnValue`, as the certificate reader refuses it; any tag was read as if it were the OCTET STRING, a recognised extension decoded from it. Found by the mutation pass.
- **fix(revocation):** a CRL or OCSP extension whose `extnValue` is not an OCTET STRING, or whose `critical` is not a BOOLEAN, is refused with `PKI_X509_STRUCTURE_INVALID` at the field, as the certificate and TSTInfo readers refuse it; every byte argument of the API is tested with `isBytes`, which accepts a `Uint8Array` from any realm, and `tests/tools/architecture.test.ts` keeps `instanceof Uint8Array` out of `src/`.
- **fix(path):** a certificate whose policies reach `maxPolicyNodes` no longer leaves the level it was growing linked from its parents; with a `user-initial-policy-set` that excludes a policy on the path, the RFC 5280 §6.1.5 (g)(iii) intersection followed those links into a level that does not exist and `validateCertificatePath` — and `buildCertificatePath` and `verifyCertificateChain` through it — threw a `TypeError` instead of reporting `PKI_REASON_LIMIT_EXCEEDED`. Found by the mutation pass.
- **feat(verify): signatures are verified lazily inside `verifyCertificateChain`** — for the links the path search is about to rely on, once each, in the order `buildCertificatePath` enumerates them and under its own `maxChainLength` and `maxPathsExplored` cuts, instead of every name-plausible pair up front. A bag of forty same-name decoys headed by the real issuer costs two verifications instead of N²; the public API, the report and every verdict are unchanged, which a test holds by running the lazy and the eager search over four shapes of bag. `signatureVerifications` in the report counts what was actually computed.
- **fix(verify): an OCSP delegated responder is judged at the response's `producedAt` as well as at `at`** (RFC 6960 §4.2.2.2): a delegate not yet valid or already expired when it signed vouched for nothing at that moment, and the response is `PKI_REASON_REVOCATION_UNKNOWN` at `ocspResponses[i]` where it was accepted before — see Verdict changes.
- **chore(api-surface): a literal union widened inside an interface member is compatible** (`scripts/lib/api-surface.ts`): `classify` treats a member whose flat union only gained literals as an addition, as ADR 0018's open unions require; it was classified incompatible until 1.0.0, which was conservative and wrong under that policy ([ADR 0018](../docs/adr/0018-what-the-1-x-promise-covers-beyond-its-snapshots.md), updated).
- **chore(registries): `schemaVersion: 1` on every `docs/data/*.json` registry**, held by the rule `registry-schema-version`; a consumer reads it before the version-specific fields ([ADR 0018 §The wire form](../docs/adr/0018-what-the-1-x-promise-covers-beyond-its-snapshots.md), updated).
- **`strict: true` refuses the first `warning` and reports every `info`.** A SHOULD the input did not follow — an end-entity certificate without a subjectKeyIdentifier, as the Web PKI's own profile asks — is advice to the issuer, and a strict reader that refused nine thousand corpus certificates for it would be one nobody could leave on; what the caller allowed (`encodingRules: 'ber'`, `mode: 'lax'`) is likewise reported and not refused.
- **ci:** no path filter on a required check; a runtime smoke test of the built package on Deno, Bun and headless Chromium (`runtimes`, required); CodeQL over the workflows, zizmor and actionlint (`workflow lint`, required); harden-runner on every job, in block mode where the endpoints are known; Dependabot with a seven-day cooldown; Dependency Review required; a weekly OSV-Scanner pass over the lockfile, alongside `npm audit`.
- **chore(release):** the release is triggered by the `v1.0.0` tag and attaches a CycloneDX and an SPDX SBOM (ISO/IEC 5962), a toolchain SBOM and the Sigstore bundle to a draft GitHub Release; `release-assets.yml` is retired. Versions 0.1.0 to 0.9.0 were milestones of the preparation of 1.0.0: each has its CHANGELOG entry and its note under `release-notes/`, and none was tagged, released or published — the first tag of this repository is `v1.0.0`.
- **docs:** SECURITY.md restructured around the compatibility promise, the supported runtimes, two private reporting channels (GitHub private vulnerability reporting and security@pkinative.dev) with the stages of ISO/IEC 29147 and 30111, what stands in place of an external audit and release integrity. The site follows pdfnative's design, with a dark palette that meets WCAG 2.2 AA where pdfnative's does not, underlined prose links, JSON-LD on every guide, and the 14 layers of 1.0 drawn from `LAYERS`.

## Conformance

- **L1** — 565 refusals, held to the frozen snapshot code for code; **L2** — every corpus certificate re-encodes byte for byte.
- **L4** — three foreign lineages; **L5** — 61 clauses against the pinned text of RFC 5280, every requirement sentence of §4.1–§4.2 accounted for and none left undiagnosed; five more inventories hold RFC 5652 (50 sentences, 44 held by a test, 6 excluded), 3161 (38; 28, 10), 6960 (23; 18, 5), 7292 (9; 7, 2) and 7468 (12; 8, 4) to their pinned texts, every exclusion with its reason and none of them `not-diagnosed`.
- **L6** — x509-limbo, 9 158/9 208; **L7** — NIST PKITS, 195/203; **L8** — S/MIME, 221/224 intact and 196/204 agreeing with NIST. Unchanged by the audit fixes: none of the corpora's verdicts moved.
- **Interop** — eight foreign implementations and two linters read every artefact the API writes, and five of those implementations write what pkinative reads; 9 tools agreed on every artefact on the Windows release machine, the Linux set runs in the conformance workflow. New in the read direction: `openssl:csr`, the eight requests `openssl req -new` writes, parsed with zero diagnostics and verified. OpenSSL 3.5.5 `cms -verify` succeeds on the frozen Ed448 SignedData sample (`cms/signed-data-ed448-shake256`).

### Verdict changes

Recorded as [ADR 0018 §The verdict table](../docs/adr/0018-what-the-1-x-promise-covers-beyond-its-snapshots.md) requires: a verdict corrected toward the standard, or a capability added, never silently. Against a 0.9.0 build of the tag:

| Input | Was | Is |
|---|---|---|
| A certificate, CRL, OCSP response or CMS signer under an id-RSASSA-PSS public key | `PKI_REASON_SIGNATURE_NOT_CHECKED` with `PKI_CRYPTO_KEY_UNSUPPORTED` (the host refused the identifier) | verified: `valid` or `PKI_REASON_SIGNATURE_INVALID`, on every runtime |
| A plain `keyBag` under an id-RSASSA-PSS certificate, in `openPkcs12` | `PKI_REASON_PKCS12_KEY_UNSUPPORTED` | opened, with `RSA-PSS` and the digest the certificate's parameters name; without parameters, `PKI_REASON_PKCS12_RSA_SCHEME_UNSPECIFIED` unless `rsaAlgorithm` names `RSA-PSS` |
| A `pkcs8ShroudedKeyBag` or a PBES2 PKCS#8 holding an id-RSASSA-PSS key | `PKI_REASON_PKCS12_KEY_UNSUPPORTED` / `PKI_CRYPTO_KEY_UNSUPPORTED` on Node.js 22 | unchanged: the host unwraps it and never hands the bytes back to re-wrap |
| An Ed448 CMS signer with the `id-shake256` digest | `PKI_REASON_SIGNATURE_NOT_CHECKED` with `PKI_CRYPTO_ALGORITHM_UNSUPPORTED`, everywhere ([ADR 0004](../docs/adr/0004-dsa-and-ed448-cms-signers-not-verified.md)) | verified on Node.js; `PKI_REASON_SIGNATURE_NOT_CHECKED` with `PKI_CRYPTO_KEY_UNSUPPORTED` where the host lacks Ed448 (Bun, Chromium) ([ADR 0022](../docs/adr/0022-ed448-cms-signers-host-dependent.md)) |
| An Ed448 CMS signer whose `digestAlgorithm` is not `id-shake256` | the same unsupported-algorithm answer | `PKI_REASON_CMS_ALGORITHM_MISMATCH` — RFC 8419 §3.1 is held |
| An OCSP response signed by a delegate not yet valid, or expired, at `producedAt` | accepted when the delegate was valid at `at` | `PKI_REASON_REVOCATION_UNKNOWN` at `ocspResponses[i]` (RFC 6960 §4.2.2.2) |

The lazy signature search changes no verdict, by construction and by test. The corpora's scores did not move; the certificates-only, countersignature, signingTime, certReq and OCSP concerns above are diagnostics, and a diagnostic is never a verdict.

## Known limitations

- **No external security audit** ([ADR 0010](../docs/adr/0010-no-external-security-audit-at-1-0.md)). None is planned: pkinative is maintained by one person. What stands in its place, evidence a reader can re-derive, is listed in [SECURITY.md](../SECURITY.md#in-place-of-an-external-audit).
- **What the promise does not cover** is listed in SECURITY.md §What is not promised: diagnostic severity and wording, message wording, limit defaults (which may be lowered in a minor), verdicts beyond the decision surface, runtimes beyond Node.js, scores, bundle sizes and performance.
- **An id-RSASSA-PSS private key under PBES2 still depends on the host**: a `pkcs8ShroudedKeyBag` or an encrypted PKCS#8 is unwrapped by Web Crypto and never handed back to re-wrap, so on Node.js 22 it stays `PKI_REASON_PKCS12_KEY_UNSUPPORTED` or `PKI_CRYPTO_KEY_UNSUPPORTED`; re-export it under `rsaEncryption` with the tool that holds it. Public keys, unencrypted PKCS#8 and plain `keyBag`s under such a certificate are no longer limited (Verdict changes).
- **What 1.0.0 does not do** — each a recorded decision or a gap, and each in the [README's known limitations](../README.md#known-limitations):
  - no fetching of CRLs or OCSP responses: the caller supplies them ([ADR 0006](../docs/adr/0006-no-network-io-in-the-engine.md)); no built-in trust store: the caller supplies the anchors;
  - Certificate Transparency SCTs are kept in their TLS encoding, neither decoded nor verified;
  - no public reader for OCSP requests or timestamp requests (a PKCS#10 request is read and verified; `verifyTimeStampToken` reads the request you hand it, internally); no writer for CRLs, OCSP responses, PKCS#8 or PKCS#12 ([ADR 0003](../docs/adr/0003-no-pkcs8-or-pkcs12-writer.md));
  - DSA signers are not verified ([ADR 0004](../docs/adr/0004-dsa-and-ed448-cms-signers-not-verified.md)); an Ed448 CMS signer is verified where the host verifies Ed448 and reported not checked where it does not ([ADR 0022](../docs/adr/0022-ed448-cms-signers-host-dependent.md)); ML-DSA keys are read, ML-DSA signatures are not verified;
  - no IDNA conversion and no public suffix list; X.520 attribute syntaxes are diagnosed, not enforced, when a name is read — a wrong string type or country size as a `warning`, a value past its upper bound or a country code outside ISO 3166-1 as `info`.
- **Outside Node.js only a smoke test runs**, on Deno, Bun and headless Chromium; Cloudflare Workers are targeted, not executed; Node.js 26 is run by an advisory workflow and promised by nothing until it enters LTS.
- **No workflow has run on GitHub yet**: the first push is the first run of CI, conformance, CodeQL, Scorecard and ClusterFuzzLite. Mutation testing runs over every executable module of `src/`, held at 100 % with argued equivalents, but by hand (`npm run mutate`), not as a gate step: a full pass is hours of machine time.

## Upgrade

**From nothing:** there was no previous release, so this is the first install.

**From a 0.9.0 build of the tag:**

- If you open an RSA `.p12`, name the scheme you used to get implicitly:

  ```ts
  const report = await openPkcs12(p12Bytes, { password, rsaAlgorithm: { name: 'RSASSA-PKCS1-v1_5', hash: 'SHA-256' } });
  ```

- If you build names, drop any `stringType: 'utf8'` you set on `countryName`, `serialNumber`, `dnQualifier`, `domainComponent` or `emailAddress`: the right type is now the default, and the old one is refused. To reproduce an existing name byte for byte, pass the value's DER as a `Uint8Array`.
- If you use `allowCommonNameFallback`, pass the validated `path` to `checkServerName`.
- If a test pinned `crl[n]` in a reason path, it is `crls[n]`.

## Downstream integration notes

- **The machine contracts, for the satellites to come.** `pkinative-cli` and `pkinative-mcp` will be built on these, and so can anything else, read at the immutable `v1.0.0` tag:
  - **`docs/assets/api.json`** — every export, its module, signature and TSDoc. Its surface is frozen by `docs/assets/api.frozen.json`.
  - **`docs/data/errors.json`** — every thrown code, with when it is raised, its remedy, its standard and its CWE. Frozen since 0.8.0 by `docs/data/errors.frozen.json`.
  - **`docs/data/reasons.json`** — every returned reason code. Grow-only: every name is frozen with the export surface, and adding one is a minor.
  - **`docs/data/diagnostics.json`** — the 97 diagnostic codes. Additions only; severity and wording may change.
  - **`schemaVersion`** — every `docs/data/*.json` registry carries `schemaVersion: 1` (rule `registry-schema-version`); read it before the fields, and treat a higher value as a shape you have not seen ([ADR 0018 §The wire form](../docs/adr/0018-what-the-1-x-promise-covers-beyond-its-snapshots.md)).
  - **`docs/data/defaults.json`** — every option default and the direction a minor may move it.
  - **The report types.** `verifyCertificateChain`, `openPkcs12`, the CMS and timestamp reports: frozen as part of the export surface; returned unions are open ([ADR 0018](../docs/adr/0018-what-the-1-x-promise-covers-beyond-its-snapshots.md)).
  - **`ecosystem.json → contracts`** — the three parts of the promise, the snapshot and rule for each, the support policy, and what is not promised.
- **New since 0.9.0:** the limit `maxPkcs12KdfIterations`; the exports `SubjectDirectoryAttributesExtension` and `DirectoryAttribute`; the extension kind `subjectDirectoryAttributes`; the option `CheckServerNameOptions.path`; the reason code `PKI_REASON_PKCS12_RSA_SCHEME_UNSPECIFIED`; fifty-seven diagnostic codes (`docs/data/diagnostics.json`, each with its `since`). No error code added or changed. The exports of the former 1.1 list, 294 in all:
  - `parseCertificationRequest(der, options?)` — a PKCS#10 request as a `CertificationRequest`; `CsrAttribute` is one attribute, values kept as DER.
  - `verifyCertificationRequest(request | der, options?)` — the proof of possession, as a `VerifyCertificationRequestReport`; `VerifyCertificationRequestOptions` extends the parse options with `allowSha1`.
  - `shake256(data, outputLength)` — SHAKE256 over public data, the length in octets.
  - `readEnumerated(node, options?)`, `readRelativeOid(node, options?)`, `encodeRelativeOid(oid)` — X.690 §8.4 and §8.20.
  - New optional members, all additive: `VerifyCertificateChainInput.onDiagnostic`, `VerifyTimeStampTokenInput.onDiagnostic`, `CheckOcspStatusInput.signer` and `CheckOcspStatusInput.onDiagnostic`. A caller who passes none sees what 0.9.0 showed, plus the diagnostics on the console.
- **Diagnostic families added at 1.0.0:** `PKI_DIAG_CMS_*` for RFC 5652 (certificates-only content, countersignature attributes, signingTime forms), `PKI_DIAG_TSP_*` for RFC 3161 (the certReq contract), `PKI_DIAG_OCSP_*` for RFC 6960 (version, certs, responderID, nocheck, unrequested SingleResponses), and the informational `PKI_DIAG_NAME_ATTRIBUTE_TOO_LONG` and `PKI_DIAG_NAME_COUNTRY_UNKNOWN`. A diagnostic never changes a verdict; `strict: true` refuses a `warning` and reports an `info`.
- **Verdict changes:** the table under Conformance — id-RSASSA-PSS keys now verify and open, Ed448 CMS signers verify on Node.js and are reported not checked elsewhere, a wrong Ed448 digest is `PKI_REASON_CMS_ALGORITHM_MISMATCH`, and an OCSP delegate out of its validity at `producedAt` is `PKI_REASON_REVOCATION_UNKNOWN`. A caller who branched on `PKI_REASON_SIGNATURE_NOT_CHECKED` for PSS-keyed issuers will now see a real verdict.
- **Runtimes:** Node.js 22 and 24 are the supported lines; Node.js 26 is tested by the advisory `node-current` workflow and promised by nothing until 2026-10-28 (`contracts.support.currentLines`).
- **No 0.x tag.** Versions 0.1.0 to 0.9.0 were milestones of the preparation of 1.0.0: each has its CHANGELOG entry and its note under `release-notes/`, and none was tagged, released or published — the first tag of this repository is `v1.0.0`. A consumer reading the tag list sees `v1.0.0` first, and it is the first version that can be installed.
- **Behaviour shifts since 0.9.0:** `PKI_REASON_REVOKED` requires authenticated, applicable evidence; URI and SmtpUTF8Mailbox names meet their constraints; the commonName fallback needs `path`; PSS keys are held to RFC 4055; the name builder's string types and bounds; PSS AlgorithmIdentifier bytes; `crls[n]` paths; whole-millisecond timestamp bounds; `KEY_USAGE_BITS` frozen. Since the final review of 2026-10-02: a trust anchor matches by name **and** key; an off-path CRL issuer must validate under the anchors; the user policy set is intersected in the anchor's domain; RSA e < 3 or even is refused; a SHA-1 timestamp imprint needs `allowSha1`; PBMAC1 keys under 20 octets are not verified; an ECDSA signing key without `namedCurve` is refused with `PKI_INVALID_OPTION` (2026-10-04) where the writers once emitted an artefact whose signature verifies `false`; v1/v2 intermediates are refused; an IP-literal `dns` reference is read as an address; an OCSP response without `nextUpdate` is stale and contradictory answers are UNKNOWN; every verdict reason from a list or a response is rooted at `crls[n]` or `ocspResponses[n]`; the implicit anchor counts against `maxChainLength`; an unknown critical CRL entry extension makes the list unusable; `createCertificate` refuses a serial of 0 or of more than 20 content octets; `addTimeStampToken` accepts a token made in another realm; a TSTInfo extension's `extnValue` must be an OCTET STRING. Since the second review of 2026-10-04: `subjectPublicKey` must be one SEQUENCE and an extension value one DER value, an Edwards `ExternalSigner` must return 64 or 114 octets, an OCSP nonce is 1 to 32 octets (`PKI_API_MISUSE`); `shake256` stops at 1 MiB and an OCSP tolerance must be a finite non-negative number (`PKI_INVALID_OPTION`).
- **Runtime floor:** `engines.node` is `^22.22.2 || ^24.14.1 || >=25.8.2`, the first releases of each line that fix CVE-2026-21713 in Web Crypto ([ADR 0017](../docs/adr/0017-runtime-and-toolchain-support.md)).
- **Semver from here:**
  - A minor release only adds.
  - A newly refused corpus certificate is a recorded fix: its release note lists it under `### Decision surface`.
  - A removal, a changed code or an incompatible signature waits for 2.0.0.
