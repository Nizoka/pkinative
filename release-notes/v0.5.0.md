# pkinative v0.5.0

> This version was prepared and never released — no tag, no GitHub Release, nothing on npm: the install instructions below describe a release that was not made.

<!-- GitHub Release title: v0.5.0 — decide a chain, and say why -->

_Released 2026-09-28_

Milestone M3. Until now pkinative **read** certificates: it told you what a certificate said, never whether to believe it. This release adds the judgement — RFC 5280 §6 path validation, path building, CRLs, OCSP, RFC 6125 host matching, extended key usage, and one call that asks every question in the right order. It also adds the third vocabulary that makes those answers usable: a `PkiReasonCode` is **returned** in a report, never thrown and never emitted, because a verification produces several reasons at once and an exception carries one. New exports; nothing removed. See **Downstream integration notes**.

## Highlights

- **`verifyCertificateChain`** — one call: every signature verified in parallel, the path built with the purpose already in hand, then the host name, then revocation. It is the only place in `src/` that turns a `PkiError` into a reason, and it never fetches anything.
- **`PkiReasonCode`, the third vocabulary** — primitives return and throw, compositions report, and exactly one layer converts. Shipped **before** the code that needed it, so nothing was ever built on `try/catch` and migrated later.
- **RFC 5280 §6 in full** — name constraints per form, the policy tree with its three counters, path length, loop detection, and a trust anchor that is judged rather than assumed. Synchronous, pure, and never throwing for a validation issue.
- **Revocation that knows what a list is *about*** — §5.2.4 delta CRLs, §5.2.5 `issuingDistributionPoint`, §5.3.3 indirect lists, and the rule that a delegated CRL signer must hold a certificate that is still good.
- **Two scored corpora, L6 and L7** — 9 156 of 9 208 x509-limbo chains and 194 of 203 NIST paths, every disagreement carrying a sentence a human wrote.

## Added

- **feat(core):** `PkiReasonCode`, the third registry, with `docs/data/reasons.json` and the `reason-parity` rule. `PKI_REASON_INPUT_MALFORMED` carries in `errorCode` the `PkiErrorCode` that *would* have been thrown — which is how a report promises never to throw for bad input without a second frozen vocabulary of 47 encoding failures.
- **feat(path):** `validateCertificatePath` — RFC 5280 §6 as an explicit state record and one function per clause. Validity, issuer chaining, signature verdicts taken precomputed, `basicConstraints`, `keyUsage`, path length, loop detection, the trust anchor, and an unrecognised critical extension refused rather than ignored.
- **feat(path):** name constraints — permitted and excluded subtrees intersecting down the path, over dNSName, rfc822Name, URI, iPAddress and directoryName, on both the subject and the SAN.
- **feat(path):** the certificate policy tree — flat levels with children by index and no parent pointers, which is what makes pruning, depth indexing and `maxPolicyNodes` tractable; `policyMappings`, `policyConstraints`, `inhibitAnyPolicy` and the §6.1.5 (g) success condition.
- **feat(path):** `buildCertificatePath` — a depth-first search with backtracking over candidate issuers, bounded by `maxPathsExplored`, which is *the* denial-of-service bound of §6: building is exponential in the candidate set and only linear in the chain length.
- **feat(path):** `checkServerName` (RFC 6125) and `checkExtendedKeyUsage` (RFC 5280 §4.2.1.12) — two questions §6 has no notion of, and the ones whose absence turns a valid certificate for somebody else into an accepted one.
- **feat(revocation):** `parseCertificateList` and `findRevocation` — the list is **walked** with a lazy TLV cursor, never decoded into nodes, so a list of millions costs constant memory.
- **feat(revocation):** `checkRevocation` — the decision, synchronous, taking a precomputed signature verdict, keeping *unknown* apart from *not revoked*, and deciding whether the list is entitled to answer at all: §5.2.5 scope, §6.3.3 (b) distribution-point matching including names given relative to the CRL issuer, §5.3.3 indirect lists, and §5.2.4 deltas read together with the base they apply over.
- **feat(revocation):** RFC 6960 OCSP in both directions — `createOcspRequest`, `parseOcspResponse`, `verifyOcspSignature` and `checkOcspStatus`, with good, revoked and unknown kept three states and the §4.2.2.2 delegated-responder rule enforced.
- **feat(verify):** `verifyCertificateChain`, in a new `verify` layer.
- **feat(hash):** `computeKeyIdentifier` — RFC 5280 §4.2.1.2 method 1, which is byte for byte RFC 6960's `issuerKeyHash`. **The input is the key bits, not the SubjectPublicKeyInfo.**
- **feat(x509):** six profile diagnostics, each a sentence addressed to the issuing CA, each measured against the corpus before it was added.

## Fixed

- **fix(verify):** a revoked intermediate was accepted, and a CRL had only one chance to be believed. Both found by NIST PKITS.
- **fix(revocation):** every CRL carrying a recognised extension was refused — a shipped defect the hand-rolled conformance harness had been hiding, and which surfaced the moment the scorer was pointed at the public entry point instead.
- **fix(path):** ten ways a name escaped its constraint, including CVE-2025-61727, plus a trust anchor that was never judged and SHA-1 signatures that were being treated as evidence. All found by scoring a corpus rather than by reading the code.

## Conformance

- **L6 — x509-limbo, scored.** 9 156 of 9 208 chains agree (99.44 %). 52 reviewed deviations, each carrying a written reason; 30 cases pinned on their `PkiReasonCode` rather than on the boolean, because *rejected for the wrong reason* is a defect no pass/fail count can see; two canaries against a scorer that stopped deciding anything. `--update-baseline` records the id it measured and **never** fills in the reason.
- **L7 — NIST PKITS.** 194 of 203 paths agree (95.57 %). A second corpus written independently, around the US Federal PKI rather than the Web PKI, pinned twice — the archive's own SHA-256 and a per-file list of what this project's ZIP reader made of it. Every one of the 405 certificates and 173 lists parses, with no refusal list at all.
- **Nine deviations remain, and one of them accepts what a standards body says to reject.** One accepts: `InvalidDNandRFC822nameConstraintsTest29` — its end-entity certificate has no subjectAltName and an `emailAddress` in its subject outside the permitted `rfc822Name` subtree, and RFC 5280 §4.2.1.10 applies the constraint to that address, which pkinative did not. Five are RFC 5280 §7.1 name comparison (encoded bytes, as Go's `crypto/x509` and webpki do), each refusing a path NIST accepts. Two are DSA, which Web Crypto does not implement; one is a suspected defect in §6.1.5's policy wrap-up, recorded alone for that reason.

## Known limitations

- **The 20 PKITS §4.8 certificate-policy tests are skipped.** Their expected result depends on a `user-initial-policy-set` the archive never states, and a runner that guessed would be scoring its own guess.
- **Names are compared by encoded bytes, not by RFC 5280 §7.1 string preparation.** Five PKITS tests turn on that difference, and the miss is a refusal. The same comparison also let a subject escape an excluded `directoryName` subtree it matched only after §7.1 preparation — an acceptance no corpus case exercises.
- **DSA is not supported and never will be** — Web Crypto implements none of it, and pkinative implements no signature algorithm itself.
- **Nothing here fetches.** Not a CRL, not an OCSP response, not a missing intermediate. A verifier that reached the network would be one an attacker can point at a host of their choosing.
- **`ValidSelfIssuedinhibitAnyPolicyTest9`** is recorded as a *suspected defect* in §6.1.5's policy wrap-up rather than an absent feature. It is the one deviation in either baseline that has not been explained.
- **ClusterFuzzLite has still never executed.**

## Upgrade

Additive for anyone on v0.4.0: no export was removed or renamed, and no parsing behaviour changed. The one thing to know before upgrading is that `PkiReason` is a **returned** value — nothing in this release throws for a validation issue, so a `try/catch` around `verifyCertificateChain` will catch nothing but a programming error.

## Downstream integration notes

- **New public API.** `validateCertificatePath`, `buildCertificatePath`, `checkServerName`, `checkExtendedKeyUsage`, `parseCertificateList`, `findRevocation`, `checkRevocation`, `createOcspRequest`, `encodeCertId`, `parseOcspResponse`, `checkOcspStatus`, `verifyCrlSignature`, `verifyOcspSignature`, `computeKeyIdentifier`, `verifyCertificateChain`, and the types they refer to. `docs/assets/api.json` lists every export with its module.
- **A third code vocabulary.** `PkiReasonCode` is disjoint from `PkiErrorCode` and `PkiDiagnosticCode`, and `docs/data/reasons.json` is its machine-readable registry. Reason messages deliberately do **not** carry the `pkinative: ` prefix — that prefix marks what is thrown, and keeping it exclusive is what lets a log reader tell an exception from a verdict.
- **New error codes and new diagnostics** are listed in `docs/data/errors.json` and `docs/data/diagnostics.json`, both checked in both directions by `verify:docs`.
- **The error vocabulary is not frozen yet.** It freezes at 0.8.0; until then a code may still be renamed in a minor release, and this note will say so when it happens.
- **Bundle cost.** `verifyCertificateChain` pulls 121 KB of the package: it reaches a key, a parser and a verdict, which is precisely why it exists. A caller who wants only the parser still pays 61 KB. `scripts/verify-bundle.ts` records every probe and the commit that measured it.
