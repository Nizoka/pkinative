# pkinative v1.1.0

_Released 2026-11-23_

The first minor of the 1.x line: additive under the compatibility promise, 100 % backward-compatible with v1.0.0 — the v1.0.0 test suite passes, as tagged, against these sources (`compat-previous`), the five patterns of `tests/compat/allow-1.0.0.json` aside: the documentation and tooling suites of the repository, and three files that enumerate a registry or a directory this release added to. It verifies ML-DSA signatures where the host does, reads back the two requests it writes, gives the verify and check verbs `strict`, and hardens the repository around the engine: Node.js 26, a release path that fails without its files, and the tooling that keeps the satellites' documentation aligned.

## Highlights

- **Post-quantum signatures verified.** ML-DSA-44/65/87 (FIPS 204) on certificates, CRLs, OCSP responses, certification requests, CMS signers and timestamp tokens, on a runtime whose Web Crypto has the algorithm (Node.js 24.7 and later); elsewhere the verdict says the signature was not checked, never that it is valid. SLH-DSA and ML-KEM public keys are read as kinds of their own.
- **Attribute certificates read.** RFC 5755 attribute certificates are parsed and their signature checked; their validation (§5) is left to the caller, and the recipe shows the composition.
- **The requests pkinative writes can be read back**: `parseTimeStampRequest` (RFC 3161) and `parseOcspRequest` (RFC 6960, with the RFC 9654 nonce).
- **`strict` reaches the verify and check verbs**, and `verifySignedData` reports its diagnostics.
- **Node.js 26 is a supported line**, tested on every pull request by `ci (26)`, a check the committed ruleset requires.
- **The 1.x promise is run, not only stated**: the previous release's own test suite runs on every pull request, a check the committed ruleset requires.

## Security

- **chore(deps-dev): eight advisories in the test toolchain closed** — vitest 4.1.12 and vite 8.2.6 (GHSA-587h-7wmj-h5pm, high, and seven more), and four in the Python interoperability pin (`pyasn1` 0.6.5). Development-only: the published package has no dependency. `picomatch` ≤ 4.0.7 (GHSA-fc5q-39xc-vjpf), reached through the test and build tools, has no patched release at the time of writing.
- **fix(agents): the guard hook resolves from `$CLAUDE_PROJECT_DIR`** ([#13]): by a relative path it stopped guarding once the shell left the repository root.
- **fix(release): a release without its files is a red run** ([#14]): the attest job fails when the release cannot be read, reads the five file names back and fetches the tarball from its public URL against the build digest; `check-npm-drift` holds the GitHub release to the same files every week. The `v1.0.0` release was published without its files attached.

## Added

- **feat(crypto): ML-DSA verification, host-dependent** ([ADR 0026](../docs/adr/0026-ml-dsa-verified-where-the-host-verifies-it.md)). Pure ML-DSA with an empty context, as RFC 9881 requires in PKIX; for a CMS signer, the digest rule of RFC 9882. One Web Crypto call, like every other signature: no post-quantum arithmetic in TypeScript.
- **feat(x509): SLH-DSA and ML-KEM public keys** read as their own kinds, with their lengths checked.
- **feat(x509): `PKI_DIAG_KEY_USAGE_KEY_ALGORITHM_MISMATCH`** (warning): a keyUsage a post-quantum key's algorithm does not allow.
- **feat(keys): `parsePrivateKeyInfo` names an ML-DSA private key**; `importPrivateKey` still refuses it.
- **feat(x509, crypto): RFC 5755 attribute certificates read and signature-checked** ([ADR 0028](../docs/adr/0028-attribute-certificates-are-read-not-judged.md)) — `parseAttributeCertificate` (holder, issuer, the six attributes of §4.4, the AC-only extensions; the profile reported through 9 `PKI_DIAG_AC_*` diagnostics; one new error code, `PKI_X509_ATTRIBUTE_MALFORMED`) and `verifyAttributeCertificateSignature`. RFC 5755 §5 validation is not implemented: there is no `verifyAttributeCertificate`.
- **feat(cms): `parseTimeStampRequest`** → `TimeStampRequest`.
- **feat(revocation): `parseOcspRequest`** → `OcspRequest`, `OcspRequestEntry`, `OcspRequestSignature`; the nonce is accepted on 1 to 128 octets (RFC 9654 §2.1). Three diagnostics: `PKI_DIAG_OCSP_REQUEST_SIGNED_UNNAMED`, `PKI_DIAG_OCSP_NONCE_LENGTH`, `PKI_DIAG_OCSP_REQUEST_EXTENSION_CRITICAL`.
- **feat(verify): `strict` on the verify and check inputs, a diagnostic sink on `verifySignedData`** ([#18], [ADR 0025](../docs/adr/0025-strict-in-the-verify-and-check-verbs.md)). In a composition (`verifyCertificateChain`, `verifyTimeStampToken`, `verifySignedData`, `openPkcs12`) a warning refused under `strict` is `valid: false` with `PKI_REASON_INPUT_MALFORMED` carrying `errorCode: 'PKI_STRICT_DIAGNOSTIC'`, never an exception; in a primitive (`checkRevocation`, `checkOcspStatus`) it throws `PKI_STRICT_DIAGNOSTIC`.
- **feat(x509): `PKI_DIAG_SPKI_ALGORITHM_UNRECOGNISED`** ([#17], info): a public key whose algorithm pkinative does not classify is still kept, and now reported.
- **ci: Node.js 26 in the matrix; `reuse lint`; `compat-previous`; an advisory `Mutation` workflow** for the `src/` files a pull request changes. `.github/rulesets/main.json` requires `ci (26)` and `compat-previous`; a ruleset binds on GitHub once the maintainer has imported it.
- **chore(tooling): satellite alignment** — `npm run satellites:sync`, the `/satellite-align` skill and the rule `satellite-stamps`.
- **chore(conformance): an RFC 5755 §4 requirement inventory** — 69 sentences, 36 held by tests, 33 excluded with a reason.
- **docs(adr):** [0024](../docs/adr/0024-what-a-satellite-may-implement.md) what a satellite may implement ([#15]); [0025](../docs/adr/0025-strict-in-the-verify-and-check-verbs.md); [0026](../docs/adr/0026-ml-dsa-verified-where-the-host-verifies-it.md); [0027](../docs/adr/0027-limit-names-are-closed-in-1-x.md) limit names are closed in 1.x; [0028](../docs/adr/0028-attribute-certificates-are-read-not-judged.md) attribute certificates are read, not judged.

- **ci: the `node-current` workflow is removed** until a Node.js line is Current again (Node 27, 2027-04-22).
- **`engines.node`** is written `^22.22.2 || ^24.14.1 || ^25.8.2 || >=26.0.0`: the same set of versions as 1.0.0.
- **docs(security): the support period of the 1.x line** ([#16]): no end date, an end announced one minor release ahead ([ADR 0017](../docs/adr/0017-runtime-and-toolchain-support.md), amended).
- **docs: the comparison with other libraries re-read from the npm registry on 2026-11-17.**
- **Package metadata**: the author's address is `hello@pkinative.dev`, and `funding` lists GitHub Sponsors beside plika.app (SUPPORT.md says what each is).
- **docs(site): the MCP explorer names the engine version it loads.** Its page said `pkinative@1.0.0` while its loader ran 1.1.0; `cdn-pin` now holds every `pkinative@x.y.z` a playground page writes, and `release-prepare` moves it. The landing page's cards name ML-DSA and attribute certificates; the README and the site's footer link to GitHub Sponsors.
- **docs(guides): migrating from node-forge or pkijs.** A twelfth guide maps each call of the two libraries to the one that replaces it, says what changes shape, and lists what has no counterpart by design; the third-party names were read in the published packages (node-forge 1.4.3, pkijs 4.0.1), and the pkinative code on the page is executed by the tests.

### Decision surface

No refusal of the frozen corpora moved (`refusals.frozen.json`: 0 new). Outside them:

- **ML-DSA signatures.** 1.0.0 reported `PKI_REASON_SIGNATURE_NOT_CHECKED` with `errorCode: 'PKI_CRYPTO_ALGORITHM_UNSUPPORTED'`. 1.1.0 verifies them where the host can, and elsewhere reports the same reason with `errorCode: 'PKI_CRYPTO_KEY_UNSUPPORTED'`.
- **An ML-DSA CMS signer whose digest RFC 9882 does not allow** is `PKI_REASON_CMS_ALGORITHM_MISMATCH`.
- **A malformed SLH-DSA or ML-KEM public key** (wrong length) throws `PKI_X509_SPKI_INVALID`; 1.0.0 kept it as `kind: 'unknown'`.
- **An ML-DSA private key** is `kind: 'ml-dsa-44' | 'ml-dsa-65' | 'ml-dsa-87'` in `parsePrivateKeyInfo`, where it was `unknown`.
- **`openPkcs12` honours `strict` and `onDiagnostic`**, which its options type already accepted and 1.0.0 ignored: under `strict`, a PKCS#12 that raises a warning is `valid: false`.
- **A call with an argument of the wrong type** throws a `PkiError` where 1.0.0 threw a `TypeError`: `PKI_INVALID_INPUT`, or the code that argument already had (an option outside its domain stays `PKI_INVALID_OPTION`). An argument, its members and the members of those are each refused where the function first reads them: a refusal 1.0.0 made for a reason of its own — a limit, an option, a misuse — still answers first where it was read first. Where 1.0.0 refused a wrong-typed value only because it resembled something else, the code is now `PKI_INVALID_INPUT`; the nine such calls are listed below. A value a reader made is told by the bytes the function reads from it and by nothing else: what 1.0.0 took, 1.1.0 takes, and a value built by hand to pass for a parsed one is not walked.
- **A signature verifier given a value without its signed members** (`tbsDer`, `signatureAlgorithm.der`, `signatureValue.bytes`, the issuer's `subjectPublicKeyInfo.der`) throws `PKI_INVALID_INPUT`. In 1.0.0 the answer depended on the member: a `TypeError`, `false` about bytes the verifier never had, or `PKI_CRYPTO_KEY_UNSUPPORTED` for an issuer without its key.
- **`matchDnsName` given a name that is not a string** throws `PKI_INVALID_INPUT`; its TSDoc said it never throws, and it threw a `TypeError`.
- **An `at` that is not a finite number** throws `PKI_INVALID_INPUT` in `validateCertificatePath`, `buildCertificatePath`, `checkRevocation`, `checkOcspStatus` and the three `verify*` compositions. A `Date` is refused with the rest: compared, it read as its time; added to a tolerance, as text. Each asks where it first reads it — `checkOcspStatus` once an answer matches, `verifySignedData` once the message is read.
- **Members 1.0.0 took whatever their type** are refused where they are read: a `staleTolerance` of `checkRevocation` that is not a number (`PKI_INVALID_OPTION`); a `purpose` of `checkExtendedKeyUsage` that is not a string, an OCSP `nonce` that is not bytes, and a list that is not an array — `crls`, `ocspResponses`, `purposes`, `initialPolicySet`, the lists of `createSignedData` (`PKI_INVALID_INPUT`). `candidates` and `certificates` are still taken as a `Set`.
- **A flag that is not a boolean** throws `PKI_INVALID_OPTION`, on every function that takes one — `requireRevocation: 'true'`, `allowSha1: 1`, `cA: 'false'`, `critical: 1`, and `null`. 1.0.0 read a flag as `=== true` or as truthy: the text `'true'` left a revocation requirement off without a word, and `cA: 'false'` encoded a CA. Leave a flag out to keep its default. `encodeBoolean` given anything but a boolean throws `PKI_INVALID_INPUT`.
- **An options argument that is not an object** — a number, a string — throws `PKI_INVALID_INPUT` where 1.0.0 read every option from it as absent. The `extensions` of `createCertificate` and `createCertificationRequest` must be an array: a `Set` or a number was dropped in silence, and the certificate issued without them.
- **Nine refusals change code**, each for a wrong-typed value 1.0.0 mistook for something else. `PKI_API_MISUSE` → `PKI_INVALID_INPUT`: `encodeSubjectAltName` and `encodeExtendedKeyUsage` given bytes instead of a list, `verifyTimeStampToken` given a number or a string. `PKI_INVALID_OPTION` → `PKI_INVALID_INPUT`: `encodeSubjectAltName` given a list whose entry is not an object. `PKI_CRYPTO_ALGORITHM_UNSUPPORTED` → `PKI_INVALID_INPUT`: a signer whose `algorithm` is not an object, in `encodeSignatureAlgorithm`, `createSignedData` and the other writers. `PKI_CRYPTO_KEY_UNSUPPORTED` → `PKI_INVALID_INPUT`: `verifyCertificateSignature` given an issuer without `subjectPublicKeyInfo.der`.
- **Two calls 1.0.0 answered are refused** with `PKI_INVALID_INPUT`: `encodeBasicConstraints` given what is not an object (it returned an empty SEQUENCE), and `openSafeContents` given what is not a `SafeContentsInfo` (it resolved `undefined`).
- **`encodeOcspCertId` and `createOcspRequest` given a digest other than SHA-1 or SHA-256** throw `PKI_INVALID_OPTION` before anything is hashed, where 1.0.0 failed later, in the OID encoder, with `PKI_INVALID_INPUT`.
- **What a reader returns is frozen throughout.** `diagnostics` is a frozen copy, and an empty `extensions`, `attributes`, `statusStrings` or `failInfo` is frozen: code that pushed onto one of them now throws.
- **One more `console.warn` line by default** for a certificate or request whose key algorithm is not classified, and for a post-quantum key whose keyUsage its algorithm does not allow — unless `onDiagnostic` is given.

## Fixed

- **fix: an argument of the wrong type is a `PkiError`, on every export.** 37 of the 108 functions of the entry point answered `undefined`, `null`, or an object whose members are not what the type says, with a `TypeError` from a property read: `createSignedData` without a signer, `checkRevocation` without an input, `parseTstInfo(undefined)`, the three `verify*` compositions. Each now throws `PKI_INVALID_INPUT` where it first reads the value (`src/core/arguments.ts`). No code is new. Twenty more wrote the refusal's message with `String(value)` and threw on an object with no prototype. `tests/fuzzing/arguments.test.ts` calls every function the entry point exports with hostile values, so an export added later is held to the same rule; `tests/fuzzing/argument-members.test.ts` starts from a valid call of each of the 108 functions and makes it wrong in one member at a time, which reaches `expected`, `limits`, `at` and the lists behind the first guard. The same suite refuses a flag that is not a boolean and a number or a string where an object, a list or bytes are expected, and reads the API manifest so that a flag added later must be named in a call.
- **fix(path): the reason for a certificate whose issuer is missing names that issuer.** A leaf whose intermediate was not supplied is still reported as `PKI_REASON_SIGNATURE_NOT_CHECKED` (`errorCode: 'PKI_CRYPTO_UNAVAILABLE'`) beside `PKI_REASON_NO_TRUST_ANCHOR` — the 1.0.0 suite holds those codes — but its message said only that no signature verdict was supplied, and the registries sent the reader to another runtime. The message now names the issuer to supply, and `reasons.json` and `errors.json` say what that pair means.
- **fix(docs): `strict` refuses a `warning`, not every diagnostic.** The option's summary in `docs/assets/api.json` (13 option types) and the `raisedWhen` of `PKI_STRICT_DIAGNOSTIC` said "every diagnostic"; an `info` has always been reported without refusing, and a verify composition reports the refusal as a reason. Four member types the manifest cut to `{` — `CheckOcspStatusInput.expected` among them — are written whole.
- **fix: everything a reader returns is frozen, the empty lists included.** `extensions`, `attributes`, `statusStrings` and `failInfo` when empty, `diagnostics` in nine readers, and the `responderId` and `certStatus` of an OCSP response were open inside results that were otherwise frozen. `tests/property/frozen-results.test.ts` walks what every `parse*` and `decode*` export returns.
- **fix(cms): `createTimeStampRequest` refuses a `hashAlgorithm` that is not a name of its table** — `__proto__` was answered with `PKI_API_MISUSE` about the hash length, and is now `PKI_INVALID_OPTION`.
- **fix(tooling): six code-scanning findings in the scripts and tests** — one `escapeRegExp` for the verify-docs rules, a private temporary directory, a trigger pattern that backtracked polynomially, a script-block filter.
- **docs: two sentences written before the first push** now say what runs.

## Conformance

- RFC 6960: the two request sentences excluded for lack of a reader are now held by tests (20 tested, 3 excluded).
- Interoperability: ML-DSA certificates and CMS cross-checked against OpenSSL 3.5 where it is installed; a tool without ML-DSA is declared absent, not failed.
- RFC 5755: a seventh requirement inventory (§4). No foreign attribute certificate was cross-checked: no graded corpus exists, and the OpenSSL at hand has no attribute-certificate command.
- Fuzz targets: 8 → 11 (`tsp-request`, `ocsp-request`, `attribute-certificate`).
- No positive ML-DSA verdict runs on Node.js 22, the gate's runtime: the `ci (24)` and `ci (26)` legs run it.

## Known limitations

- **ML-DSA is verified, not written**: no ML-DSA signing in the writers and no ML-DSA private-key import (ADR 0026 says when that is revisited). SLH-DSA signatures are not verified.
- **The Certificate Transparency SCT list** is still kept in its TLS encoding.
- **Attribute certificates are read, not judged**: no RFC 5755 §5 validation — holder binding, targeting and AC revocation are the caller's ([ADR 0028](../docs/adr/0028-attribute-certificates-are-read-not-judged.md)).
- **No CRL or OCSP-response writer.**

## Upgrade

No export left and no signature changed incompatibly — two output unions widened (`OctetPublicKeyInfo.kind`, `PrivateKeyKind`) and five input types gained optional members, all recorded by the ratchet of `api.frozen.json` — and the v1.0.0 test suite passes as tagged (five excluded patterns aside): a drop-in replacement for v1.0.0, with three tightenings: a malformed SLH-DSA or ML-KEM public key, which 1.0.0 kept as `kind: 'unknown'`, is now refused; a member of the wrong type that 1.0.0 took in silence — an `at` that is a `Date`, a tolerance that is text, a list that is not an array, a flag that is not a boolean, options that are not an object — is refused (**Decision surface**); and what a reader returns is frozen throughout. Read **Decision surface** above if you branch on `errorCode`, parse PKCS#12 files under `strict`, or assert that parsing emits no diagnostic.

## Downstream integration notes

For pkinative-cli and pkinative-mcp, which pin `pkinative ^1.0.0` and vendor its registries:

- **Registries to re-vendor**: `docs/data/errors.json` (57 → 58 codes: `PKI_X509_ATTRIBUTE_MALFORMED`), `docs/data/diagnostics.json` (97 → 111 codes; `PKI_DIAG_OCSP_VERSION_NOT_V1` now cites "RFC 6960 §4.1.1, §4.2.2.3"), `reasons.json`, `limits.json` (`guards` text only), `defaults.json`, `surfaces.json` (a capability may be `pending` on a satellite), and for the CLI `api.frozen.json` (329 exports) and `errors.frozen.json`.
- **Neither satellite type-checks against 1.1.0 until it follows three additions.** The new error code: pkinative-cli maps every `PkiErrorCode` in `src/utils/pkierr.ts` (`satisfies Record<PkiErrorCode, Mapping>`), pkinative-mcp in `src/data/pkinative/code-tables.ts` and `src/pki-errors.ts`. The 14 new diagnostic codes: pkinative-mcp types a table against `PkiDiagnosticCode` (`code-tables.ts`). The widened `PrivateKeyKind`: both pass it to a parameter typed with the five kinds of 1.0.0 (`pkinative-cli/src/utils/signer.ts`, `pkinative-mcp/src/signer.ts`).
- **The published satellites keep running**: their `^1.0.0` pin resolves 1.1.0 on a fresh install, and nothing they call raises the new error code. Three things differ until their next release. An ML-DSA private key given to a signing command is refused as an RSA key that lacks its scheme, where it was refused as an unknown key. A certificate with an SLH-DSA or ML-KEM key reports a `kind` the CLI's published report schema does not list. The MCP server's `describe_engine` goes on listing the 57 error codes and 97 diagnostic codes it vendored.
- **New key kinds**: `OctetPublicKeyInfo.kind` gains fifteen values (twelve `slh-dsa-…`, three `ml-kem-…`) and `PrivateKeyKind` three (`ml-dsa-44`, `ml-dsa-65`, `ml-dsa-87`). A satellite that enumerates the kinds — a report schema, a `switch` — adds them.
- **New exports not reached yet**: `parseTimeStampRequest`, `parseOcspRequest`, `parseAttributeCertificate`, `verifyAttributeCertificateSignature` — the CLI's "every runtime export reached" matrix is incomplete until its next minor. Proposed: `tsp inspect-request`, `ocsp inspect-request`; `acert inspect`, `acert verify-signature`; MCP `inspect_timestamp_request`, `inspect_ocsp_request`, `inspect_attribute_certificate`, `verify_attribute_certificate_signature`.
- **`strict`**: both satellites already spread `strict` into `openPkcs12`, so `--strict` on a PKCS#12 with a warning now yields `valid: false`; read `errorCode === 'PKI_STRICT_DIAGNOSTIC'`. The CLI's extra parse in `cms verify` is no longer needed; its `escalateStrict` helper still is, for bag-certificate warnings.
- **ML-DSA**: a verdict that was `PKI_CRYPTO_ALGORITHM_UNSUPPORTED` becomes a verification or `PKI_CRYPTO_KEY_UNSUPPORTED` — update any table of "not checked" causes.
- **Arguments of the wrong type**: no code is new, so nothing is to be mapped. `errors.json` widens the `raisedWhen` and `remedy` of `PKI_INVALID_INPUT` and the `raisedWhen` of `PKI_INVALID_OPTION` (re-vendor). A satellite that forwards a caller's value — an MCP tool argument, a CLI flag parsed to the wrong type — now receives a `PkiError` where the engine threw a `TypeError`. The promise covers an argument, its members and theirs; a value edited by hand to pass for a parsed one is outside it. `at` is a number of milliseconds: a satellite that parses a date passes its `getTime()`. A flag is a boolean: a CLI flag or an MCP argument that reaches the engine as the text `'true'` is now `PKI_INVALID_OPTION`, where it was read as off.
- **`engines.node`** is the same range, written differently; Node.js 26 is a supported line, and `node-current.yml` is gone.
- **Satellite surface contract**: each satellite is asked to commit `docs/assets/surface.json` at release (issue drafts in each repository), which `npm run satellites:sync` reads in contract mode.
